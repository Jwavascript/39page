# 0012. 재생 실패는 종류별로 설명하고, 늦은 사건보다 조용한 실패를 더 경계한다

- 상태: 채택
- 날짜: 2026-11-03

## 배경

M3-5 는 "재생이 안 되는 경우를 전부 사용자에게 설명한다" 가 목표다. 네 가지가
서로 당겼다.

1. **오류 코드가 여섯 가지**다 (2 · 5 · 100 · 101 · 150 · 153). 승인된
   프로토타입은 한 문장에 번호만 붙인다. 번호만으로는 사용자가 할 수 있는 일을
   알 수 없다.
2. **API 스크립트 로드 실패를 재시도해야 한다.** 그런데 M3-1 은 "실패를 담아둬
   다음 요청이 즉시 실패로 끝나게" 했다 — 실패한 `<script>` 가 `error` 를 다시
   쏘지 않아 요청이 영원히 매달리는 것을 막기 위해서였다. 그 결정 그대로는
   재시도가 **영구히 불가능**하다.
3. **늦게 도착한 비동기 사건**이 현재 트랙의 상태를 덮어쓸 수 있다.
4. **영상 로딩 전 안내**(`.video-placeholder`)를 띄워야 하는데, 그 자리는
   어댑터가 소유한다 (ADR 0002).

## 결정

### 1. 안내는 **도메인 종류**로 가르고 번호를 함께 보여준다

숫자 → 종류 변환은 어댑터가 이미 한다 (`PlayerErrorKind`). 코디네이터는
종류별로 **사용자가 다음에 할 일**을 적고, 끝에 번호를 붙인다.

| 종류                | 사정                    | 안내가 가리키는 행동    |
| ------------------- | ----------------------- | ----------------------- |
| `invalid-parameter` | 2 — 잘못된 영상 ID      | 링크를 다시 등록        |
| `not-playable`      | 5 — HTML5 재생 불가     | YouTube 에서 열기       |
| `not-found`         | 100 — 삭제·비공개       | (알림만)                |
| `embed-not-allowed` | 101 · 150 — 임베드 불허 | YouTube 에서 열기       |
| `referrer-missing`  | 153 — Referer 없음      | (알림만)                |
| `api-unavailable`   | 스크립트 로드 실패      | 네트워크 확인 후 ▶ 다시 |
| `unknown`           | 문서에 없는 코드        | 다음 곡 직접 선택       |

101 과 150 이 같은 문장인 것은 같은 사정이기 때문이다. 번호는 사용자가
검색하거나 알려줄 수 있는 유일한 단서라서 승인된 디자인처럼 함께 보여준다.
스크립트 로드 실패에는 번호가 없다.

### 2. 로더는 실패한 시도를 **버리고 실패한 요소를 치운다**

M3-1 의 결정을 바꾼다. 실패를 담아두는 대신

- 싱글턴 Promise 를 비우고,
- 그 시도가 지켜본 `<script>` 를 **DOM 에서 제거한다.**

그래서 다음 요청은 죽은 요소를 보지 않고 **새 요청**이 된다. M3-1 이 걱정한
"영원히 매달림" 은 요소를 치우는 것으로 해결되고, "요청 폭풍" 은 재생 시작
경로가 전부 사용자의 명시적 동작이라는 사실로 해결된다 — API 를 못 받으면
아무것도 재생된 적이 없어 `ENDED` 자동 전환도 일어나지 않는다.

`window.onYouTubeIframeAPIReady` 는 **모듈 수명 동안 한 번만** 감싼다.
재시도마다 다시 감싸면 래퍼가 중첩된다. 어댑터도 실패 시 `apiRequested` 를
풀어 다음 `load()` 가 다시 요청하게 한다.

### 3. 자동재생 차단은 **낙관적 `loading` 만** 되돌린다

어댑터는 `YT.Player` 를 만들며 `loading` 을 스스로 세운다. 자동재생이 막히면
그 단정이 거짓이 된다. 그대로 두면 토글이 ⏸ 를 보여주고, 누르면 "멈춤" 이
되어 **사용자가 재생을 다시 요청할 수 없다.** 그래서 `loading` 일 때만
`idle`(CUED 와 같은 값)로 되돌린다. YouTube 가 이미 알려준 상태는 건드리지
않는다 — "상태의 진실은 YouTube" 라는 M3-1 의 원칙은 유지된다.

### 4. 늦은 사건은 **버릴 수 있는 것만** 버린다

| 사건                        | 버리는 조건                            |
| --------------------------- | -------------------------------------- |
| 모든 사건                   | 그 어댑터의 연결이 끊겼다 (`detach()`) |
| `ENDED`                     | 그 트랙이 재생된 적이 없다 (M3-2)      |
| `error` · `autoplayBlocked` | 큐가 비어 있다 — 붙일 트랙이 없다      |

연결이 끊긴 뒤의 사건은 **코디네이터가 연결마다 따로 감싼 핸들러**로 막는다.
실제 어댑터도 세대 번호로 자기 콜백을 무효화하지만(M3-1), 그것은 어댑터의
약속이다. 코디네이터가 어댑터의 성실함에 기대지 않는다.

**오류는 "이미 재생됐다" 는 이유로 버리지 않는다.** 그 규칙을 한 번 넣어봤다.
코드 2·5·100·101·150·153 이 전부 적재 시점의 실패이므로 재생 중에 오는 오류는
이전 적재의 늦은 신호라는 추론이었다. 되돌렸다 — 그 규칙은 재생 중에 생긴
진짜 오류를 **조용히 삼킨다.** 화면은 `재생 중` 인데 소리는 나지 않는 상태가
되고, 이것이 M3-5 가 없애려는 바로 그 "조용한 실패" 다. 틀린 안내는 사용자가
보고 판단할 수 있지만, 없는 안내는 그럴 수 없다.

**남는 한계**: IFrame API 는 사건에 적재 식별자를 주지 않는다. `load(B)` 직후
`B` 의 첫 상태가 오기 전에 도착한 `A` 의 오류는 `B` 의 것으로 보인다. 창은 수
밀리초이고, `B` 가 실제로 재생되면 `stateChange('playing')` 이 안내를 지워
저절로 바로잡힌다. 더 좁히려면 API 쪽 지원이 필요하다.

### 5. 로딩 전 안내는 어댑터 소유 영역의 **형제**다

승인된 레퍼런스는 `.video-holder` 안에 `.video-placeholder` 와 `.yt-host` 를
형제로 둔다. 같은 구조를 쓴다. Vue 가 소유하는 `.video-holder` 가 테두리·비율·
최소 크기를 잡고, 그 안에 안내와 `.player-mount` 가 형제로 놓인다. Vue 는
`.player-mount` **안**을 여전히 건드리지 않는다.

안내는 `v-if` 가 아니라 **클래스로 숨긴다.** 레퍼런스도 `.hidden` 토글을 쓴다.
이 컴포넌트에서는 조건부 렌더를 아예 쓰지 않는 쪽이 안전하다 — `v-if` 하나가
영상 영역 쪽으로 옮겨 붙기만 해도 iframe 이 재로드되고, 정적 검사가 그 금지를
그대로 지킬 수 있다.

### 6. `YOUTUBE에서 열기 ↗` 는 곡을 고른 뒤 **항상** 보인다

레퍼런스와 같다. 오류일 때만 띄우면 재생이 깨지는 순간 링크가 "새로 나타나"
레이아웃이 흔들리고, 재생되는 영상도 YouTube 에서 열어볼 이유가 있다.
주소는 `shared/utils/youtube.ts` 의 `youtubeWatchUrl()` 이 만들며 영상 ID 를
**다시 검증**한다. 형식이 아니면 `null` 이고 링크를 띄우지 않는다.
`target="_blank"` 에는 `rel="noopener noreferrer"` 를 함께 붙인다.

### 7. 재생 중인 트랙이 지워지면 멈추고 알린다 — 큐는 그대로

`MVP_SPEC.md` F4 의 정책이다. 큐는 스냅샷이라 라이브러리를 고쳐도 자동으로
끊기지 않는다. 그래서 **Record Library UI 가 사실만 알리고**
(`trackRemoved(trackId)`), 멈출지는 코디네이터가 정한다. 드로어는 여전히
`playback` store 도 `PlayerAdapter` 도 모른다.

큐는 바꾸지 않는다. 여기서 큐를 손대면 "재생 중 목록을 편집해도 큐가 흔들리지
않는다" 는 보장이 무너진다. 자동으로 다음 곡으로 넘기지도 않는다 — 사용자가
방금 뭔가를 지웠고, 그 결과로 다른 곡이 울리기 시작하면 놀란다 (M3-0.7 과 같은
이유).

## 대안

| 대안                                           | 왜 택하지 않았는가                                                                             |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 번호만 보여주는 한 문장 (프로토타입 그대로)    | 사용자가 할 수 있는 일을 알 수 없다. 임베드 불허와 삭제된 영상은 전혀 다른 상황이다            |
| 코드 숫자로 직접 분기                          | YouTube 숫자값이 어댑터 밖으로 새어나간다 (ADR 0008 위반)                                      |
| 실패를 담아두고 재시도 버튼으로 로더를 초기화  | 초기화 API 를 밖으로 내보내야 한다. 실패한 요소를 치우면 초기화가 저절로 된다                  |
| 오류 상태를 `playback` store 에 더 쌓는다      | 기존 `statusMessage` / `statusTone` 으로 충분하다. 새 상태를 만들지 않는다 (M3-3 과 같은 판단) |
| 재생 중 트랙 삭제 시 큐에서도 뺀다             | 스냅샷 보장이 무너진다. 사용자가 보는 큐 위치(`2 / 5`)가 삭제마다 흔들린다                     |
| 안내를 `.player-mount` 안에 absolute 로 띄운다 | Vue 가 `YT.Player` 가 교체하는 영역을 패치하게 된다 (ADR 0002)                                 |
| 오류일 때만 외부 링크를 띄운다                 | 레이아웃이 흔들리고, 레퍼런스의 동작과도 다르다                                                |

## 결과

- 여섯 가지 오류 코드가 각각 다른 안내를 받고, 번호도 함께 보인다.
- API 로드 실패 뒤 ▶ 를 다시 누르면 **새 스크립트로 재시도**한다. 스크립트는
  언제나 문서에 하나뿐이고, `YT.Player` 도 하나뿐이다.
- 자동재생이 막히면 토글이 ▶ 로 돌아가 사용자가 다시 요청할 수 있다.
- 연결이 끊긴 어댑터는 store 를 더 이상 건드리지 못한다.
- 재생 중인 곡을 지우면 멈추고 알린다. 큐와 라이브러리의 분리는 유지된다.
- `.player-mount` 의 DOM 소유권은 그대로다. 안내는 그 형제다.
- **남은 한계**: 적재 식별자가 없어 트랙 전환 직후 수 밀리초의 오류 오귀속
  가능성이 있다. 재생이 시작되면 저절로 지워진다.
