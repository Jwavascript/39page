# 0003. 최소 Widget Registry / Widget Host를 M1에 도입한다

- 상태: 채택
- 날짜: 2026-11-02
- 관련: `docs/architecture/SYSTEM_DESIGN.md` §5, `docs/architecture/THEME_SYSTEM.md` §7

## 배경

장기 목표로 위젯 추가·삭제·이동·크기 변경과 개별 위젯 스킨 조합을 지원해야 한다.
MVP 레이아웃은 승인된 프로토타입 그대로 고정이다.

고정 레이아웃을 컴포넌트에 하드코딩하면, 나중에 동적 레이아웃을 도입할 때
컴포넌트 트리를 다시 써야 한다. 플레이어가 그 트리 안에 있으면 재작성 과정에서
규칙 5(재생 상태 보존)가 깨질 위험이 크다.

## 결정

**M1에 레지스트리와 호스트 구조만 도입한다. 편집 UI는 만들지 않는다.**

- `WidgetDefinition`: 종류별 메타데이터 + `resolve({ theme, skin })` 컴포넌트 해석
- `WidgetRegistry`: 종류 → 정의 조회
- `WidgetInstance`: `instanceId`로 식별되는 배치된 위젯
- `WidgetHost`: 레이아웃을 순회해 인스턴스를 렌더링
- `DashboardLayout`: MVP에서는 **모듈 상수**. 사용자가 편집할 수 없고 저장하지 않는다

호스트 규칙 4개를 함께 확정한다.

1. `:key`는 `instanceId`만 사용한다. 인덱스·테마·스킨을 넣지 않는다.
2. 모든 인스턴스는 그리드 컨테이너의 직계 자식이다. 배치는 CSS로만 지정한다.
3. `persistent: true` 위젯은 테마에 따라 컴포넌트를 교체하지 않는다.
4. 알 수 없는 `kind`는 조용히 건너뛴다.

테마와 스킨은 **독립된 두 축**으로 둔다. 스킨은 자체 색을 하드코딩하지 않고
테마 토큰을 참조하므로 두 축이 곱집합으로 조합된다.

## 대안

| 대안                                                              | 탈락 이유                                                                   |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 고정 레이아웃을 컴포넌트에 하드코딩하고 백로그 단계에서 전면 교체 | 플레이어를 품은 트리를 재작성해야 한다. 규칙 5가 깨질 위험                  |
| M1에 편집 UI까지 구현                                             | MVP 범위 밖이다. `MVP_SPEC.md` §3에서 제외했다                              |
| 기성 대시보드 레이아웃 라이브러리 도입                            | 대부분 DOM 노드를 재배치해 iframe을 파괴한다 (ADR 0002). 필요성도 아직 없다 |

## 결과

- M1의 컴포넌트 트리가 MVP(M5) 전체와 백로그 단계까지 유지된다.
  레이아웃 상수를 store로 바꾸는 것이
  주된 변경이 된다.
- `:key` 규칙이 규칙 5를 지키는 핵심 장치가 된다. 리뷰 시 확인 항목이다.
- MVP에서는 쓰이지 않는 추상화가 일부 존재한다 (`movable`, `resizable`,
  `skins`). 의도된 비용이며, 구현하지 않은 기능을 완료로 표시하지 않는다
  (`AGENTS.md` 규칙 9).
