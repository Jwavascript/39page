# 0018. JSON 백업 파일은 저장 봉투를 품고, 가져오기는 승인 전까지 읽기 전용이다

- 상태: 채택 (M8-2 내보내기 · M8-3 가져오기 구현. 개정 절 둘)
- 날짜: 2026-11-06
- 관련: [`0007-library-data-protection.md`](0007-library-data-protection.md),
  [`../architecture/BACKUP_FORMAT.md`](../architecture/BACKUP_FORMAT.md),
  [`../architecture/SYSTEM_DESIGN.md`](../architecture/SYSTEM_DESIGN.md) §7,
  [`../development/POST_MVP_PLAN.md`](../development/POST_MVP_PLAN.md) §B.12

## 배경

MVP 가 배포됐고 Post-MVP 의 첫 항목으로 JSON 백업·복원을 정했다.
`POST_MVP_PLAN.md` §B.12 가 이미 이것을 **B-0** 으로 추천했다 — 의존성 0,
서버 0, 계정 0 이고 "데이터가 날아갈까" 에 즉시 답한다.

지금 유실되는 경로는 세 가지다 (같은 문서 §0 실측).

| 상황                                 | 지금    | 백업이 해결하는가      |
| ------------------------------------ | ------- | ---------------------- |
| 새로고침 · 재시작                    | 보존    | — (이미 해결)          |
| 브라우저 사이트 데이터 삭제 · 시크릿 | 유실    | **해결** (파일을 보관) |
| 다른 기기 · 다른 브라우저            | 안 보임 | **해결** (수동 이전)   |
| origin 변경                          | 안 보임 | **해결** (수동 이전)   |

영속 데이터는 `39page.library` 와 `39page.theme` **두 키**뿐이다. 둘 다
`{ version, data }` 봉투이고, 라이브러리의 검증기 `normalizeLibraryData` 는
이미 **순수 함수**이며 무엇을 버렸는지 보고한다.

설계의 과제는 포맷을 발명하는 것이 아니라 **이미 있는 보장을 파일 경계
밖으로 끌고 나가는 것**이다.

## 결정

### 1. 파일은 자기 식별자와 자기 버전을 갖는다

```json
{ "format": "39page-backup", "schemaVersion": 1, "exportedAt": "…", "data": { … } }
```

`format` 이 틀리면 파싱된 JSON 이라도 거부한다. 다른 앱의 JSON 을 "구조가
비슷하니" 받아들이는 일이 생기면 안 된다.

### 2. 섹션은 저장 봉투를 **그대로** 품는다

`data.library` 는 `39page.library` 에 들어가는 값과 같은 모양이다.

```json
"library": { "version": 1, "data": { "playlists": [], "selectedPlaylistId": null } }
```

이 선택이 ADR 전체에서 가장 큰 효과를 낸다 — 가져오기가
`normalizeLibraryData(section.data)` 한 줄로 끝난다. M2 의 검증 규칙을 복사하지
않으므로 **두 경로가 어긋날 수 없다.**

### 3. 파일 버전과 내부 버전을 분리한다

`schemaVersion` 은 파일 **구조**를, 섹션 `version` 은 **내용 스키마**를 센다.
라이브러리 스키마가 2 로 올라가도 파일 포맷은 1 이다.

**선택 섹션을 더하는 것은 `schemaVersion` 을 올리지 않는다.** 이것이 Music
Moments(M9)의 확장 경로이며, 올리지 않는 덕분에 **구형 앱도 그 파일에서
라이브러리를 복원할 수 있다.** 모르는 섹션은 건너뛰고 그 사실을 알린다.

### 4. 상위 버전은 거부하고, 하위 버전은 읽는다

저장 계층과 같은 정책이다 (`SYSTEM_DESIGN.md` §7.1). 앞으로 되돌릴 수 없다.
거부는 파일을 손대지 않으므로 사용자가 최신 앱에서 다시 열면 된다.

섹션 하나가 미래 버전이어도 **파일 전체를 버리지 않는다.** 그 섹션만 건너뛴다.

### 5. 승인 전까지 `localStorage` 를 만지지 않는다

```
선택 → 크기 → parse → 봉투 → 섹션 검증 → 미리보기 → 충돌 확인 → 승인 → 저장
                                                                    ↑
                                                       여기서 처음 쓴다
```

저장 계층의 "읽기는 쓰지 않는다" 를 가져오기에도 적용한 것이다. 미리보기가
기존 데이터를 건드리지 않으므로, 사용자는 **무엇이 들어오고 무엇이 버려지는지
본 뒤에** 결정한다.

### 6. 마이그레이션은 저장 계층과 가져오기가 **같은 함수**를 쓴다

지금은 `migrate` 가 없다. 내부 버전을 올리는 작업에서 마이그레이션을
`defineStorage` 옵션 안에 익명으로 두면 가져오기 경로가 호출할 수 없고,
규칙이 둘로 갈라진다.

**순수 함수로 따로 내보내고 양쪽이 그것을 가리킨다.** 지금 지킬 규약이고,
`defineStorage` 는 바꾸지 않는다.

### 7. 부분 가져오기를 허용한다 — 단 명시적 동의로

ADR 0007 은 **일부만 복구된 `localStorage`** 에 쓰기를 막는다. 가져오기는
허용한다. 판단 기준이 "되돌릴 수 있는가" 로 **같기 때문**이다.

| 상황                     | 원본 위치              | 부분 반영의 결과             |
| ------------------------ | ---------------------- | ---------------------------- |
| `localStorage` 일부 복구 | `localStorage` 자신    | 덮어쓰면 **영구히 사라진다** |
| 백업 파일 일부 유효      | **파일** (사용자 보관) | 파일은 그대로 남는다         |

조건은 **버리는 항목을 미리보기에 적는 것**이다. `normalizeLibraryData` 의
`report` 가 그 목록이다 — 새로 세지 않는다.

### 8. 보호 상태에서도 가져올 수 있다 (새 액션)

ADR 0007 이 "범위에 없다" 고 남긴 **"기존 데이터를 버리고 새로 시작"** 이
바로 이것이다. `protected` 에서 가져오기를 막으면 백업이 가장 필요한 순간에
막힌다.

- 라이브러리 store 에 `replaceAll` 을 더한다. 평범한 수정 경로의 보호는 그대로
- 확인 문구가 **읽을 수 없는 원본을 덮어쓴다는 사실**을 말한다
- 그 전에 **원본 원문 내려받기**를 제공한다. 우리가 해석 못 해도 사용자는 보관할 수 있다
- 성공하면 `status` 가 `ready` 로 바뀐다 — 사용자가 원본을 버리기로 결정한 것이다

### 9. 원자성을 약속하지 않는다. 순서와 결과를 약속한다

`localStorage` 에는 여러 키 트랜잭션이 없다. 그래서 **가치 순으로 쓴다.**

```
1. 현재 원문을 메모리에 보관
2. 39page.library   ← 되돌릴 수 없는 데이터
3. 39page.theme     ← 최선 노력
```

`setItem` 은 키 하나에 대해 전부 쓰거나 전혀 쓰지 않는다. 그래서 **뒤가 실패해도
앞을 되돌릴 이유가 없다.** 테마는 다시 고르면 되고, 라이브러리를 되돌리면
사용자가 방금 승인한 복원을 우리가 취소하는 것이 된다. 되돌리는 경우는
**쓴 뒤 다시 읽었을 때 깨진** 하나뿐이고, 그때 1 의 원문을 되돌려 쓴다.

**새 저장 키를 만들지 않는다.** ADR 0007 이 백업 키를 탈락시킨 이유(키 증가와
생애주기 규칙)를 되풀이하지 않는다. "실수로 가져왔다" 는 확인 단계의
**내보내기 선행** 한 번으로 막는다 — 기능이 자기 자신으로 스스로를 보호한다.

### 10. M8 은 **전체 교체만** 지원한다

병합은 id 충돌·중복 곡·이름 중복·선택 상태 **네 가지 정책**과 그만큼의 UI 를
요구한다. 교체만으로 백업·복원이 완결되고, 교체의 유일한 위험(현재 데이터
손실)은 확인 + 내보내기 선행으로 막을 수 있다. 병합의 위험(결과를 예측할 수
없음)은 UI 로 막기 어렵다.

병합이 진짜 필요한 때는 **두 기기에서 각각 쌓은 목록을 합치는 것**이고 그것은
동기화의 문제다. 백업 파일로 흉내내면 충돌 해결 UI 를 두 번 만든다.

**포맷은 그대로 두고 나중에 더할 수 있다.** 가져오기 방식은 포맷이 아니라
적용 단계의 선택지다.

### 11. 테마는 넣고, 적용은 선택이다

`POST_MVP_PLAN.md` §B.11 은 **동기화** 대상에서 테마를 뺐다. 백업은 다르다 —
"내 설정을 다시 세운다" 이므로 들어 있는 것이 유용하다. 파일에는 넣고
가져올 때 켜고 끌 수 있게 한다. 두 정책이 충돌하지 않는다.

### 12. 백업 파일은 동기화 수단이 아니다

명시적으로 만들고 명시적으로 가져오는 **스냅샷**이다. M10 의 Chrome 확장과
웹앱 사이 전달에 이 파일을 쓰지 않는다. 자동으로 읽고 쓰기 시작하면 충돌
해결과 시계 문제가 따라오고, 그것이 `POST_MVP_PLAN.md` §B 가 다루는 영역이다.

## 대안

| 대안                                                | 탈락 이유                                                                                                  |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 섹션에 봉투 없이 `LibraryData` 를 그대로 넣는다     | 파일 버전과 내부 버전을 구분할 자리가 없어진다. 내부 스키마가 바뀌면 파일 버전을 올려야 한다               |
| `localStorage` 원문(문자열)을 그대로 덤프한다       | 키 이름과 봉투가 파일 포맷이 되어 **내부 구조를 영구히 고정**한다. 사람이 읽기도 어렵다                    |
| `schemaVersion` 없이 `app.version` 으로 호환성 판단 | 앱 버전과 파일 구조는 다른 축이다. 포맷이 안 바뀐 릴리스마다 호환성 표가 늘어난다                          |
| 선택 섹션 추가에도 `schemaVersion` 을 올린다        | Moments 를 쓰기 시작한 순간부터 구형 앱이 **라이브러리조차** 복원할 수 없다                                |
| 가져오기 전 현재 데이터를 백업 키에 복사해 둔다     | 키가 늘고 생애주기를 정해야 한다 (ADR 0007 이 같은 이유로 탈락시켰다). 내보내기 선행이 더 단순하고 명확    |
| 검증 실패 항목을 조용히 버리고 가져온다             | 사용자가 무엇을 잃었는지 모른다. ADR 0007 과 `MVP_SPEC.md` F9 의 방향과 어긋난다                           |
| 검증 실패가 하나라도 있으면 파일 전체를 거부한다    | 500곡 중 1곡 때문에 복원을 포기하게 된다. 파일은 되돌릴 수 있으므로 과하다                                 |
| `protected` 에서는 가져오기를 막는다                | 백업이 가장 필요한 순간에 막힌다                                                                           |
| M8 에서 병합까지 구현한다                           | 정책 4개와 UI 가 늘고, 진짜 필요한 때는 동기화다. 최소 기능을 먼저 (지시서의 방향과 같다)                  |
| 파일 크기 상한을 두지 않는다                        | 악의적·사고성 거대 파일이 파싱 단계에서 탭을 멈춘다. 8 MiB 는 5만 곡 이상이라 정당한 백업을 막지 않는다    |
| 플레이리스트·트랙 **개수** 상한을 둔다              | 정당한 백업을 거부할 위험이 크다. 실제 한계는 바이트와 `localStorage` 용량이고 후자는 쓰기 결과가 알려준다 |

## 결과

### 좋아진 것

- **`normalizeLibraryData` 를 그대로 재사용한다.** 가져오기 전용 검증 규칙이
  생기지 않으므로 M2 와 M8 이 어긋날 수 없다
- ADR 0007 이 남긴 TODO("명시적 초기화 조작")가 닫힌다
- 기기 이전·사이트 데이터 삭제 복구가 **계정·서버 없이** 가능해진다.
  `POST_MVP_PLAN.md` §B 의 계정 스택을 올리는 동안의 보험이 된다
- Moments(M9)와 레이아웃 저장(백로그)이 **파일 버전을 올리지 않고** 들어온다

### 비용과 위험

- store 에 `replaceAll` 이 생긴다. 보호 우회 경로이므로 **가져오기 외에서
  부르면 ADR 0007 이 무의미해진다.** 테스트로 호출 지점을 고정해야 한다
- 전체 교체만 지원하므로 "두 기기의 목록 합치기" 는 아직 할 수 없다
- 파일은 **평문**이다. 플레이리스트 이름과 영상 ID 가 그대로 보인다. 개인정보로
  볼 만한 것은 없지만 사용자에게 "이 파일은 누구나 읽을 수 있다" 를 알려야 한다
- 브라우저의 다운로드·파일 선택 동작은 플랫폼마다 다르다. 특히 iOS Safari 의
  다운로드와 안드로이드 Chrome 의 파일 선택은 **실기기 확인이 필요하다** (M8-4)

### 아직 정하지 않은 것

- ~~내보내기·가져오기 UI 자리~~ — **M8-2 에서 결정했다.** 레코드 편집 시트의
  바닥이고, 승인된 값을 바꾸지 않도록 드로어 토큰만 재사용한다
  (`BACKUP_RESTORE.md` §5)
- 라이브러리 내부 버전을 2 로 올릴 때의 마이그레이션 함수 모양 (결정 6 의 규약만 정했다)
- Moments 의 도메인 모델 (M9)

## 개정 (2026-11-06, M8-2) — 선택 필드 `integrity` 추가

내보내기를 구현하면서 결정 하나가 더 필요해졌다.

**보호·접근 실패 상태에서도 내보낼 수 있어야 한다** — 그때가 백업이 가장
필요한 순간이다. 그런데 그렇게 받은 파일을 나중에 **온전한 전체 백업으로
오인하면** 사용자가 잃은 것을 모른 채 덮어쓴다.

```json
"integrity": { "library": { "level": "recovered", "reason": "partial-recovery" } }
```

- **선택 필드이므로 `schemaVersion` 은 1 그대로다** (결정 3 의 규칙)
- **온전할 때는 필드를 넣지 않는다.** 평범한 백업의 모양이 M8-1 예시와 같다
- `reason` 의 네 값은 `LibraryProtectedReason` 과 **같다** (ADR 0007).
  다섯째 `unavailable` 은 저장소 자체를 쓸 수 없는 경우다
- **쓰기 실패는 복구본이 아니다.** 그때 메모리는 저장소보다 더 온전하다 —
  불완전한 쪽은 저장소이고 파일이 아니다. UI 안내로만 다룬다
- 복구본은 **확인 단계를 거친다.** 사용자가 복구본임을 알고 받아야 한다

호환성 영향은 **없다.** 모르는 리더는 무시하고 라이브러리를 정상 복원한다.
M8-3 의 가져오기가 이 필드를 읽어 미리보기에 "복구본" 을 띄운다.

## 개정 (2026-11-06, M8-3) — 가져오기에서 더 정한 것

설계에 없던 네 가지가 구현에서 필요해졌다. 모두 **데이터 안전성** 쪽으로
정했다.

### 13. 라이브러리 교체에 성공하면 재생을 멈추고 큐를 비운다

큐는 스냅샷이고, 라이브러리를 편집해도 흔들리지 않는 것이 그 성질이다
(`MVP_SPEC.md` F4). 그런데 **통째로 교체되면** 큐가 가리키는 라이브러리 자체가
사라진다 — 계속 재생하면 사용자가 목록에서 찾을 수 없는 곡이 흐르고,
다음·이전은 없는 트랙 사이를 오간다. 스냅샷을 지키는 것이 오히려 혼란이 되는
유일한 경우다.

코디네이터 계약에 `libraryReplaced()` 를 더했다. 가져오기는 **사실만** 알리고
멈출지 말지는 코디네이터가 정한다 — `trackRemoved()` 와 같은 구조다 (규칙 4).

**실패한 복원 때문에 재생을 멈추지 않는다.**

### 14. 미리보기 이후의 변경은 지문으로 잡는다

미리보기를 뜰 때 `{ store 상태, 39page.library 원문, 39page.theme 원문 }` 을
떠 두고, 적용 직전에 다시 떠서 비교한다. 다르면 적용하지 않고 다시 확인시킨다.

**저장소 원문까지 보는 이유:** 다른 탭이 저장소를 바꾸면 이 store 는 알지
못한다 (`storage` 이벤트를 듣지 않는다). store 만 보면 놓친다.

미리보기는 **열린 채로 남긴다.** 사용자가 바뀐 내용을 비교한 뒤 다시 누를 수
있어야 한다.

### 15. 안전한 복원을 보장할 수 없으면 막는다

보호 상태인데 저장소에 접근할 수 없으면 원본을 **꺼낼 수도 덮어쓸 수도** 없다.
그 상태로 진행하면 "복원했다" 고 말하면서 아무것도 하지 못한다. 미리보기
단계에서 막고 이유를 적는다 — 최종 버튼이 비활성이 된다.

### 16. 저장 계층에 읽기 전용 메서드 둘을 더한다

| 메서드        | 왜                                                                     |
| ------------- | ---------------------------------------------------------------------- |
| `raw()`       | 해석하지 못한 원본을 **파일로 넘겨주기** 위해. `read()` 로는 못 꺼낸다 |
| `available()` | `raw()` 의 `null` 이 "값 없음" 과 "저장소 못 씀" 을 구분하지 못한다    |

쓰기 경로·봉투 형태·`STORAGE_KEYS` 는 **그대로다.** 매체를 아는 쪽이 저장
계층이므로 호출부가 `localStorage` 를 직접 만지지 않아도 된다.

### 결정 7 의 확인 — 부분 가져오기는 그대로 허용한다

`readBackup` 이 `normalizeLibraryData` 의 `report` 를 그대로 경고로 옮긴다.
버리는 개수와 사유가 미리보기에 뜨고, 그것을 본 상태에서만 승인된다.
새로 세지 않는다 — M2 가 이미 세고 있었다.
