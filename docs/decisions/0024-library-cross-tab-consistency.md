# 0024. 라이브러리는 쓰기 직전에 저장소 원문을 기준과 비교하고, 다른 탭의 변경을 storage 이벤트로 반영한다

- 상태: 채택 — **M10-3A (2026-11-11)** · **보완: ADR 0025** (M10-3 안정화 — 잠금 +
  영수증으로 아래 "한계" 의 동시 쓰기를 협력하는 탭 사이에서 막는다. 결정 8 · 9 도 바뀌었다:
  `replaceAll` 은 잠금 안에서 `expectedRaw` 를 다시 보고, Moments 도 같은 정합성을 갖는다)
- 관련: **ADR 0007** (라이브러리 데이터 보호), **ADR 0018** (백업·복원 — 가져오기의
  신선도 검사), **ADR 0023** 결정 4 (M10-3 의 선행 조건),
  `docs/architecture/SYSTEM_DESIGN.md` §7.2

## 배경

라이브러리 store 의 `persist()` 는 메모리 상태 **전체**를 쓰고, 다른 탭이 그 사이에
쓴 것을 확인하지 않았다. 두 탭이 열려 있으면 나중에 쓴 탭이 이긴다 — 탭 A 가
열린 채 탭 B 가 트랙을 추가하면, A 의 **다음 변경(목록 선택 하나라도)** 이 B 의
트랙을 조용히 지웠다.

M9 까지는 "같은 앱을 두 탭에 여는" 드문 경우였다. M10-3 Quick Add 는 확장이 새
탭에서 수집 화면을 열고 그 탭이 저장하므로 **이 경로가 일상이 된다**
(ADR 0023 결정 4).

조건 (Batch 2 지시):

- 저장 키·스키마를 바꾸지 않는다
- 충돌하면 조용히 저장하지 않고 최신 확인·재시도를 안내한다
- `protected` · `unavailable` 보호 정책(ADR 0007)을 유지한다
- 대시보드의 모든 라이브러리 변경 경로에 적용한다

## 결정

### 1. 기준 원문 — 마지막으로 읽거나 쓴 원문

store 가 `baselineRaw` 를 기억한다. `restore()` 가 읽을 때와 쓰기가 성공했을 때
갱신한다. 원문 문자열을 그대로 비교하므로 스키마가 바뀌지 않는다.

### 2. 쓰기 전에 두 번 비교한다

- **변경 액션의 첫 줄** (`staleGuard`) — 생성 · 이름 변경 · 삭제 · 선택 · 트랙
  추가 · 삭제 · 이동 · 이름 변경 8개 모두. 낡았으면 최신을 다시 읽고 `conflict`
  로 거절한다. "지운 목록에 추가" 같은 낡은 판단을 하기 전에 멈춘다.
- **`persist()` 직전** — 같은 동기 실행 안이라 보통 겹치지만, 나중에 가드를 빠뜨린
  액션이 생겨도 여기서 막힌다. 다르면 메모리의 이번 변경을 버리고 다시 읽는다.

충돌이면 **이 탭은 쓰지 않는다.** 다른 탭의 변경이 저장소에 그대로 남고, 이 탭은
최신을 보여 주며 "다른 탭에서 바뀌어 최신 내용을 불러왔어요. 이번 변경은
저장하지 않았으니 확인 후 다시 해 주세요." 라고 알린다. 링크 추가 폼은 입력값을
지우지 않는다 — 그대로 다시 누를 수 있다.

### 3. storage 이벤트로 화면을 최신으로

`watchExternalChanges()` 가 라이브러리 키(또는 전체 비우기)의 `storage` 이벤트를
듣고, 원문이 기준과 다르면 다시 읽는다. `main.ts` 가 복원 뒤 부른다.
**진짜 방어는 2번이다** — 이벤트는 다른 탭이 쓴 **뒤에 비동기로** 오므로, 그 사이의
조작은 2번이 막는다.

### 4. 다시 읽기는 `restore()` 그대로 — 보호 정책 유지

다른 탭이 쓴 값이 손상됐거나 미지원 버전이면 이 탭도 `protected` 가 되어 쓰기를
멈춘다(새 버전 앱이 다른 탭에서 쓴 경우). 반대로 보호 상태의 탭은 다른 탭이 읽을
수 있는 값(예: 백업 복원)으로 바꾸면 `ready` 로 돌아온다.

### 5. 선택은 탭마다 지킨다

다시 읽을 때 이 탭이 고른 목록이 아직 있으면 그대로 둔다. 다른 탭에서 목록을 고를
때마다 이 탭의 드로어가 바뀌면 놀랍다. 다음 쓰기 때 이 탭의 선택이 저장되지만
데이터를 잃지는 않는다.

### 6. 저장소에 접근할 수 없게 된 것은 다른 탭의 변경이 아니다

`raw()` 의 `null` 은 "비었다" 와 "못 읽는다" 를 구분하지 못한다. `available()` 이
거짓이면 비교하지 않고 메모리를 지킨다 — 쓰기가 실패하고 "저장되지 않음" 으로
알리는 기존 동작(ADR 0007) 그대로다. (처음 구현에서 이것을 빠뜨려 기존 통합
테스트가 잡았다 — 메모리 목록이 빈 목록으로 바뀌었다.)

### 7. 저장하지 못한 변경이 다시 읽기로 사라지면 알린다

쓰기 실패 · 보호 상태의 세션 전용 변경이 남아 있을 때 다른 탭의 변경을 다시 읽으면
그 변경은 사라진다. `externalChange.discardedUnsaved` 로 남기고 상태 배너가
"이 탭에서 저장하지 못했던 변경은 반영되지 않았습니다" 라고 적는다. 다음 저장이
성공하면 내린다.

### 8. 백업 가져오기(`replaceAll`)는 가드 대상이 아니다

사용자가 미리보기를 보고 승인한 **의도적 교체**다. 미리보기 뒤 다른 탭이 바꿨는지는
가져오기 경로가 이미 검사한다 (ADR 0018, M8-3). 쓴 뒤 기준 원문만 옮긴다.

### 9. Moments store 는 이번에 바꾸지 않는다

Batch 2 지시가 "기존 Moments 저장 기능은 변경하지 않는다" 이다. Moments 도 같은
"나중에 쓴 탭이 이긴다" 구조이므로 **같은 한계가 남는다** (TODO, M10-4 전에 결정).
Quick Add 는 라이브러리만 쓰므로 이번 경로에는 해당하지 않는다.

## 한계 — 원자적이지 않다

`localStorage` 에는 탭 사이의 트랜잭션이 없다. 각 탭(렌더러)은 다른 탭의 쓰기를
**비동기로** 전달받는다. 그래서 두 탭이 **서로의 쓰기를 받기 전에** 각각
"비교 → 쓰기" 를 하면 둘 다 통과하고, 나중에 도착한 쓰기가 앞의 것을 덮는다.

이 결정은 위험한 창을 **"그 탭을 다시 불러올 때까지"(분~시간)** 에서 **"쓰기가 다른
탭에 전달되는 시간"** 으로 줄인다.

**실측 (M10-3C, Chromium 155, 같은 브라우저의 대시보드 두 탭, 운영과 같은 빌드)**

| 잰 것                                      | 결과                                                                   |
| ------------------------------------------ | ---------------------------------------------------------------------- |
| 한 탭의 쓰기가 다른 탭 저장소에 보이기까지 | **6.5–23ms** (10회씩 두 번)                                            |
| 두 탭이 **같은 순간** 쓰기 (간격 0)        | 처음 측정 20회 중 **20회 한쪽을 잃음** · 감지 추가 뒤 10회 중 9회 잃음 |
| 간격 5ms                                   | 10회 중 잃음 0 — 3회는 `conflict` 로 막혔고 7회는 둘 다 저장           |
| 간격 10 · 20 · 50 · 100ms                  | 각 10회, 잃음 0 — 둘 다 저장                                           |

즉 위험한 창은 **약 5ms 안**이다. 사람이 두 탭을 번갈아 누르는 속도로는 닿지 않지만,
닿으면 막지 못한다.

### 막지 못한 덮어쓰기를 성공처럼 남기지 않는다 (M10-3C)

간격 0 에서 처음에는 두 탭이 모두 "저장했다" 를 보고했고 한쪽 곡이 조용히 사라졌다.
막을 방법(스키마 없이 탭 간 원자성)은 없으므로 **알리는 것**을 더했다.

- **대시보드** — 이 탭이 방금(1초 안) 쓴 값을 다른 탭의 저장이 덮으면
  (`storage` 이벤트의 `oldValue` = 이 탭이 쓴 원문) `externalChange.possiblyOverwritten`
  를 세우고 상태 배너가 "다른 탭과 거의 동시에 저장했습니다 — 이 탭의 마지막 변경이
  덮였을 수 있습니다" 라고 적는다. 다른 탭이 이 탭의 쓰기를 **보고 나서** 사람이
  거기서 고치는 데는 1초보다 걸리므로 그 경우는 표시하지 않는다(시간이 지난 뒤의
  덮어쓰기는 정상 편집). 1초 안에 두 탭에서 일부러 고치면 거짓 경보가 날 수 있다 —
  "확인해 주세요" 안내일 뿐이다.
- **수집 화면** — 저장한 곡의 id 가 목록에서 없어지면 "추가했습니다" 를 내리고
  "방금 추가한 곡이 목록에서 없어졌습니다" 로 되돌려 다시 추가할 수 있게 한다.
  시간 추정 없이 곡이 있는지만 본다 (다른 탭에서 지운 경우도 같은 안내).
- 실측: 간격 0 의 잃은 쓰기 **9회 모두** 잃은 탭이 표시했다. 수집 화면과 대시보드의
  동시 저장에서도 잃은 쪽(대시보드)이 표시했다.

| 대안                                   | 기각 이유                                                                                                 |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `revision` 필드로 낙관적 잠금          | 저장 스키마가 바뀐다 (버전 올림·마이그레이션) — 이번 조건이 금지한다. 그래도 전파 지연은 남는다           |
| Web Locks 로 쓰기 직렬화               | 잠금을 잡아도 다른 탭의 마지막 쓰기가 **이 렌더러에 도착했다는 보장이 없다** — 비교가 여전히 낡을 수 있다 |
| BroadcastChannel 로 한 탭만 쓰게(리더) | 리더 선출·인계·탭 종료 처리가 커진다. 메시지도 비동기라 같은 창이 남는다                                  |
| IndexedDB 트랜잭션                     | 저장 매체를 바꾼다 — 백업·복원·보호 정책 전체를 다시 설계해야 한다. 범위 밖                               |

## 결과

- 다른 탭이 저장한 트랙·이름·삭제를 낡은 탭이 조용히 지우지 않는다 (사람이 두 탭을
  번갈아 쓰는 속도에서는 막힌다).
- 낡은 탭의 변경은 한 번 거절되고 사용자가 다시 해야 한다 — 자동 병합하지 않는다.
- 같은 앱을 두 탭에 열면 서로의 변경이 이벤트로 바로 보인다.
- 남은 위험: 전파 지연 창(실측 약 5ms) 안의 동시 쓰기 — 막지 못하고 **알린다**.
