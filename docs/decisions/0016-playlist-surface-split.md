# 0016. 플레이리스트와 트랙을 두 표면으로 나누고, 플레이리스트는 위젯으로 꺼낸다

- 상태: 채택 (2026-11-06 일부 개정 — 트리거와 타일 역할 재배치)
- 날짜: 2026-11-04

## 배경

M6 의 실기기 검증에서 라이브러리에 대해 네 가지가 보고됐다
(`docs/development/M6_PLAN.md` §0).

| #   | 보고                                                                   |
| --- | ---------------------------------------------------------------------- |
| 6a  | 노래를 추가하려면 무엇을 눌러야 하는지 찾느라 헤맸다                   |
| 6b  | `이름 수정` 이 플레이리스트 이름을 바꾸는데 트랙 이름으로 읽혔다       |
| 6c  | 이미 저장한 레코드의 이름을 바꿀 방법이 없다                           |
| 7   | 플레이리스트와 트랙이 한 요소 안에 있어 둘 중 하나만 길어져도 늘어난다 |

네 보고가 **한 구조에서 나왔다.** 드로어 한 열에 전부 쌓여 있었다.

```
[＋ 새 목록] [＋ YouTube 링크 추가]   ← 위계가 다른 둘이 동급으로 나란히
플레이리스트 목록                     ← 길어지면 아래를 밀어낸다
[▶ 목록 전체 재생] [이름 수정] [삭제]  ← '이름 수정' 이 트랙 목록 바로 위
트랙 목록                             ← 그래서 트랙 이름으로 읽힌다
```

위계가 **공간에 드러나지 않는 것**이 6a·6b 의 원인이고, 두 목록이 **같은
스크롤을 공유하는 것**이 7 의 원인이다. 그래서 문구를 고치는 것으로는 닫히지
않는다.

## 결정

### 1. 표면을 둘로 나눈다

| 표면                                  | 담당                                                       |
| ------------------------------------- | ---------------------------------------------------------- |
| **플레이리스트 위젯** (대시보드 위젯) | 타일 격자. 생성. 전체 재생. **자기 안에서 스크롤**         |
| **편집 오버레이** (기존 드로어 자리)  | 한 목록의 트랙. 이름 변경·삭제, 레코드 추가·순서·이름 변경 |

사용자 구상은 바탕화면의 **폴더 아이콘**이다. 타일을 누르면 그 목록이 전체
재생되고, `⋯` 로 그 목록의 레코드가 오른쪽 오버레이에 열린다.

이 분리가 네 보고를 한꺼번에 닫는다.

- **6a** `＋ 새 목록` 은 플레이리스트가 사는 위젯으로, `＋ YouTube 링크 추가` 는
  트랙이 사는 오버레이로 갔다. 둘이 나란히 설 자리가 없어졌다.
- **6b** `이름 수정` 은 **목록 이름이 적힌 머리말** 옆에 있다. 트랙 목록 바로
  위에 남은 것은 트랙 추가뿐이다.
- **6c** 트랙 행에 `✎` 를 더했다 (`library.renameTrack`).
- **7** 두 표면이 각자 스크롤한다. 한쪽이 길어져도 다른 쪽을 밀지 않는다.

### 2. 위젯은 `src/features/library/` 에 둔다

`M6_PLAN.md` 의 초안은 `src/widgets/playlist/` 였다. 디렉터리 규약을 다시 읽고
바꿨다 — `src/widgets/` 는 clock·weather 처럼 **도메인과 무관한 독립 위젯**
자리이고, 플레이리스트 관리는 라이브러리 도메인이다. 데크
(`src/features/deck/DeckWidget.vue`)가 같은 선례다.

레지스트리는 `src/widgets/registry.ts` 에 그대로 있고 컴포넌트만 가리킨다.

### 3. 빈 목록의 타일은 재생이 아니라 **열기**다

비어 있으면 재생할 것이 없다. 타일을 비활성으로 두면 작은 `⋯` 말고는 들어갈
길이 없는 **막다른 길**이 된다 — 6a 가 바로 그 종류의 문제였다.

그래서 빈 타일은 편집 오버레이를 연다. 그림도 `▶` 가 아니라 `＋` 이고, 접근성
이름도 "열기 — 비어 있음" 이라고 말한다. 같은 모양이 두 일을 하는 위험은
**이름과 그림이 각각 사실을 말하는 것**으로 막는다.

### 4. 여는 조작은 보이는 버튼이 본체이고, 길게 누르기는 추가 경로다

사용자는 "꾹 누르고 있거나 혹은 어떤 동작을 하면" 이라고 했다. 롱프레스만
두면 키보드·스크린리더에 대응되는 동작이 없어 M5 접근성 기준을 통과하지
못한다. 그래서 타일마다 보이는 `⋯` 버튼을 두고, 타일 자체의 `contextmenu`
(안드로이드 Chrome 의 길게 누르기, 데스크톱의 우클릭)를 **같은 핸들러**로
연결했다.

### 5. 위젯은 플레이어와 같은 열에 둔다

```
'deck   player   clock'
'deck   player   weather'
'mascot playlist .'
```

3열(정보)까지 넓히지 않은 것은 의도다. 우측 오버레이 드로어가 3열 안에서
끝나므로, 플레이리스트를 2열에 두면 **편집 오버레이가 열려 있어도 타일이
가려지지 않는다.** 한 목록을 편집하면서 다른 목록으로 건너갈 수 있다.

좁은 화면에서는 플레이어 아래 행 전체를 쓴다.

### 6. 선택이 바뀌면 오버레이는 작성 중인 것을 닫는다

선택을 바꾸는 곳이 이제 오버레이 **밖**이다. 머리말은 새 목록을 가리키는데
폼이 옛 목록을 겨냥한 채 열려 있으면 사용자가 어디에 쓰는지 알 수 없다.

`linkTargetId` 가 폼이 열릴 때 대상을 붙잡는 것은 **그대로 둔다.** 폼이
살아남는 경로가 생겨도 잘못된 목록에 트랙이 들어가지 않게 하는 방어선이다.

## 대안

| 대안                               | 왜 아닌가                                                                                              |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 문구와 버튼 위치만 고친다          | 7 이 닫히지 않는다. 두 목록이 같은 스크롤을 공유하는 한 한쪽이 길어지면 다른 쪽이 밀린다               |
| 드로어를 탭 두 개로 나눈다         | 한 번에 하나만 보인다. 사용자 구상(타일을 누르면 재생)과 어긋나고, 재생하려면 라이브러리를 열어야 한다 |
| 플레이리스트를 헤더의 드롭다운으로 | 목록이 길어지면 같은 문제가 드롭다운 안으로 옮겨간다. 폴더 메타포도 사라진다                           |
| 타일에 삭제 버튼도 둔다            | 되돌리기 어려운 동작을 재생 타일 한 칸 옆에 두게 된다. 이름이 보이는 오버레이 머리말이 더 안전하다     |
| 빈 타일을 비활성으로 둔다          | 막다른 길이 된다 (위 §3)                                                                               |
| 롱프레스만으로 편집을 연다         | 키보드·스크린리더 경로가 없다 (위 §4)                                                                  |

## 결과

### 좋아진 것

- 보고 6a·6b·6c·7 이 모두 닫혔다. 구조로 닫혔으므로 문구를 다시 고칠 일이 없다
- 드로어가 842 줄에서 줄었고 트랙 행이 `TrackList.vue` 로 분리됐다 (규칙 3)
- 플레이리스트를 **재생하려고 라이브러리를 열 필요가 없어졌다.** 세로 화면의
  재생 경로가 하나 더 늘었다 (M6-3 과 같은 방향)

### 비용

- 승인된 레퍼런스에 플레이리스트 위젯이 없다. **레퍼런스 이탈**이고 사용자
  확인을 받았다 (규칙 6). 색·조판은 레퍼런스의 행·드로어 토큰을 그대로 재사용해
  새 색을 만들지 않았다
- `PlaylistList.vue` 를 지웠다. 드로어에 플레이리스트 목록이 없어졌다
- 좁은 화면에서 오버레이가 열리면 타일이 함께 숨는다 (스테이지가 플레이어만
  남기므로). 목록을 바꾸려면 닫아야 한다 — 오버레이 머리말이 어느 목록인지
  말하므로 길을 잃지는 않는다
- 위젯이 한 줄 더 생겨 "스크롤 없이 한 화면" 이 폰에서 더 빡빡해졌다. 위젯
  높이에 상한(`--size-playlist-max-height`)을 두어 늘어나지는 않게 했다

### 아직 확인되지 않은 것

실기기 확인이 남아 있다. 특히 타일 두 칸이 폰 세로에서 실제로 읽히는지는
jsdom 에서 확인할 수 없다.

## 개정 (2026-11-06, M7)

실기기에서 써 본 뒤 **트리거와 타일의 역할을 바꿨다.** 결정의 뼈대(두 표면으로
나눈다, 위젯이 플레이리스트를 갖고 오버레이가 트랙을 갖는다)는 그대로다.

| 조작                 | M6-4·5            | M7                                |
| -------------------- | ----------------- | --------------------------------- |
| 데크(LP·카세트) 누름 | 트랙 드로어 열기  | **플레이리스트 위젯 펼치기/접기** |
| 타일 본문 누름       | 그 목록 전체 재생 | **그 목록의 트랙 편집 열기**      |
| 타일 `⋯`             | 트랙 편집 열기    | 없어짐                            |
| 타일 `▶`(우측 상단)  | 없음              | **그 목록 전체 재생**             |
| 길게 누르기          | 편집(추가 경로)   | 없어짐                            |

왜 바꿨나: 사용자가 "lp판을 누르면 최소화 되었던 playlist 위젯이 펼쳐지게",
"플레이리스트를 눌렀을 때는 해당 설정 드로어가 겹쳐 올라오게" 를 요청했다.

따라 온 결과:

- **§3 의 판단이 뒤집혔다.** "빈 목록의 타일은 재생이 아니라 열기" 는 본문이
  재생이었을 때의 예외였다. 이제 본문이 **항상** 편집을 열므로 예외가 필요
  없어졌고, 빈 목록에서는 `▶` 가 비활성이다. 막다른 길이 아니다 — 본문으로
  들어가 레코드를 넣을 수 있다
- **§4 의 접근성 논증이 적용되지 않는다.** 롱프레스를 보조 경로로 둘 이유가
  본문 한 번 누름으로 사라졌다
- **§5 의 배치가 바뀌었다.** 위젯이 플레이어 열(2열)에서 **데크 아래(1열)** 로
  옮겼다. 데크가 이 위젯을 펼치므로 둘이 붙어 있어야 무엇이 열렸는지 눈으로
  따라갈 수 있다. 3열(정보)을 비워 두는 것은 그대로이므로 **오버레이가 타일을
  덮지 않는다는 보장은 유지된다**
- 세로 오버레이는 **하단 고정 시트**가 됐다. 겹침 보장을 다시 세워야 했다 —
  `docs/development/M7_PLAN.md` §4
- 접힘/펼침 상태가 생겼다. 데크와 위젯이 떨어져 있어 주입으로 잇는다
  (`playlistShelfController.ts`)

재생 경로는 넷으로 유지된다: 타일 `▶`, 드로어 `▶ 목록 전체 재생`, 트랙별 `▶`,
데크 트랜스포트 `▶`. 실수 재생이 없어진 것이 덤이다.
