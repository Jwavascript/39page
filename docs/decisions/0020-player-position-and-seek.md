# 0020. 재생 시점 조회와 이동은 어댑터 계약에 더하고, 코디네이터가 중계한다

- 상태: 채택 — **M9-3 에서 구현·실측 (2026-11-10)**
- 날짜: 2026-11-07
- 관련: **ADR 0006** (어댑터 소유권), **ADR 0008** (어댑터 이벤트 계약),
  **ADR 0009** (Playback Coordinator), **ADR 0011** (가시성 가드),
  **ADR 0012** (재생 실패 처리), **ADR 0019** (Moment 도메인),
  `docs/architecture/MOMENTS_DESIGN.md` §4

## 배경

Moment 를 저장하려면 **지금 몇 초인지** 알아야 하고, Moment 로 가려면
**그 초로 옮겨야** 한다. 현재 `PlayerAdapter` 계약에는 둘 다 없다.

```ts
mount() · destroy() · load(videoId, options?) · play() · pause() · state()
```

M3 가 일부러 뺀 것이다. 다만 **뺀 것은 "우리가 만드는 탐색 바 UI"** 였다
(`IMPLEMENTATION_PLAN.md` 3.1 — "자체 탐색 바·볼륨 UI 를 만들지 않는다").
YouTube 네이티브 컨트롤이 스크럽을 제공하고 우리는 그것을 가리지 않는다
(개발자 정책 III.I.6). 프로그램으로 특정 시점에 가는 것은 다른 이야기다.

이 ADR 은 **어느 계층에 넣는가**를 정한다.

## 결정

### 1. 어댑터가 시점을 책임진다

```ts
interface PlayerAdapter {
  // ... 기존 여섯 개

  /**
   * 현재 재생 위치(초). 준비 전이거나 적재된 영상이 없으면 `null`.
   * 숫자를 지어내지 않는다.
   */
  position(): number | null

  /** 적재된 **같은 영상** 안에서 지정한 초로 이동한다. */
  seek(seconds: number): void
}
```

어댑터여야 하는 이유는 기존 계약의 이유와 같다. YouTube 특이사항을 밖으로
새지 않게 하는 것이다 (`AGENTS.md` 규칙 4, ADR 0006). `getCurrentTime()` 은
플레이어가 준비되기 전에 `0` 을 돌려주거나 던진다 — 그 사정을 아는 곳은
어댑터뿐이고, 밖에는 **`null` 이라는 도메인 값**으로만 보여야 한다.

`null` 이 중요하다. `0` 을 돌려주면 호출부가 "영상 맨 앞" 과 "아직 모른다"
를 구분할 수 없고, 사용자는 **0초짜리 Moment** 를 얻는다.

`FakePlayerAdapter` 도 같은 계약을 실제로 구현한다 (기존 방침 그대로).

### 2. 영상 전환은 `seek` 이 아니라 `load` 의 인자로 한다

```ts
interface PlayerLoadOptions {
  autoplay?: boolean
  /** 이 초부터 시작한다. 생략하면 처음부터. */
  startSeconds?: number
}
```

다른 영상의 Moment 로 갈 때 `load()` 후 `seek()` 을 부르면 경쟁이 생긴다 —
새 영상이 준비되기 전의 `seek` 은 **이전 영상에 적용되거나 사라진다.**
어댑터가 `load` 를 보류하듯 `seek` 도 보류 큐를 따로 가져야 하고, 둘의
순서까지 보장해야 한다.

`loadVideoById({ videoId, startSeconds })` 는 **YouTube 가 공식으로 주는
인자**다. 보류 중인 `load` 하나에 시점이 같이 실려 있으므로 경쟁할 것이
없고, 0:00 에서 점프하는 장면도 보이지 않는다.

그래서 두 경로를 나눈다.

| 상황                   | 하는 일                                           |
| ---------------------- | ------------------------------------------------- |
| **지금 영상**의 Moment | `seek(atSeconds)` + `play()` — 다시 적재하지 않음 |
| **다른 영상**의 Moment | `load(videoId, { autoplay: true, startSeconds })` |

같은 영상을 다시 `load` 하지 않는 것이 중요하다. 재적재는 버퍼링을 다시
일으키고, 사용자에게는 같은 곡이 끊기는 것으로 보인다.

### 3. UI 는 어댑터를 부르지 않는다 — 코디네이터에 면을 하나 더한다

```ts
export interface PlaybackMoments {
  /**
   * 지금 재생 중인 영상의 시점을 찍는다.
   * 재생할 영상이 없거나 플레이어가 아직 모르면 `null`.
   */
  capturePosition(): MomentCapture | null

  /** Moment 가 가리키는 지점부터 재생한다. */
  playMoment(target: { videoId: string; atSeconds: number }): PlayRequestResult
}
```

`PlaybackRequests` · `PlaybackTransport` 와 같은 자리다. Moments 위젯은
어댑터도 YouTube API 도 모른 채 이 둘만 부른다 (ADR 0009).

**`playMoment` 가 `PlayRequestResult` 를 돌려주는 것이 핵심이다.** 다른 재생
요청과 **같은 가시성 가드**를 통과한다 (ADR 0011) — 플레이어가 가려져 있으면
같은 문구로 거절되고, M7-2 의 `stepAside()` 로 시트가 먼저 비켜주는 흐름도
그대로 쓴다. Moment 재생만 예외인 경로를 만들지 않는다.

`capturePosition()` 이 `null` 이면 저장 버튼은 **비활성**이다. 시점을 모르는
채로 Moment 를 만들지 않는다.

### 4. 시점은 **누를 때** 찍는다

저장 버튼을 누른 순간 `capturePosition()` 이 값을 고정한다. 메모를 다 쓴
뒤에 다시 읽지 않는다.

메모를 20초 동안 쓰면 재생은 20초 흘러간다. 저장 시점에 읽으면 사용자가
표시한 순간과 저장된 숫자가 어긋난다 — 그 20초가 바로 사용자가 "이 부분"
이라고 생각한 구간을 지나간 시간이다.

### 5. 정확히 그 초에서 시작한다

`atSeconds - 2` 처럼 앞당기지 않는다. 목록에 `1:23` 이라 적어두고 `1:21`
부터 틀면 표시와 동작이 어긋나고, 어긋남의 크기를 사용자가 조절할 수도 없다.

> 대안으로 "도입 2초" 를 검토했다. 음악적으로는 더 나을 때가 있지만,
> 그러려면 저장값과 재생값이 달라진다는 사실을 UI 가 설명해야 한다.
> 숫자를 하나만 두는 쪽을 택했다.

### 6. 확장(M10)을 위한 모양

`capturePosition()` 은 **이 탭의 플레이어**를 보지만, Moment 를 만드는 함수는
그렇지 않다.

```ts
createMoment({ videoId, atSeconds, note, title, now, id }): Moment
```

입력을 전부 명시로 받는 순수 함수다. "지금 재생 중인 것" 을 암묵적으로
읽지 않으므로, YouTube 페이지에서 확장이 모은 값으로도 같은 함수를 쓸 수
있다 (지시서 E). 확장과 웹앱 사이의 **전달 방식은 M10 에서 설계한다**
(`BACKUP_FORMAT.md` §6-3).

## 경계 사례

| 사례                            | 처리                                                                                           |
| ------------------------------- | ---------------------------------------------------------------------------------------------- |
| API 이벤트 지연 · 준비 전       | `position()` 이 `null`. 저장 버튼 비활성. 숫자를 지어내지 않는다                               |
| 영상 전환 중 저장               | 전환 후 `ready` 전까지 `null` 이므로 같은 경로로 막힌다                                        |
| 재생 불가 영상의 Moment         | 기존 실패 경로 그대로 (ADR 0012). **Moment 를 지우지 않는다** — 자동 삭제 금지                 |
| 자동재생 차단                   | 기존 `autoplayBlocked` 안내. Moment 누름은 사용자 제스처라 보통은 닿지 않는다                  |
| `atSeconds` 가 영상 길이보다 큼 | 막지 않는다. 저장 시점에 다른 영상의 길이를 알 수 없다. 재생은 끝으로 가고 `ENDED` 로 처리된다 |
| 플레이어가 가려져 있음          | 다른 재생 요청과 **같은** 거절 (ADR 0011)                                                      |

## 대안

| 후보                                            | 탈락 이유                                                                          |
| ----------------------------------------------- | ---------------------------------------------------------------------------------- |
| **어댑터에 `position`/`seek`** (채택)           | 위                                                                                 |
| 컴포넌트가 `YT.Player` 를 직접 부름             | 규칙 4 위반. YouTube 특이사항이 UI 로 샌다. ADR 0006 이 금지한 소유권 침범         |
| 코디네이터가 `getCurrentTime` 을 직접 폴링      | 어댑터를 우회한다. 숫자 상태값을 밖에서 해석하게 된다                              |
| `load()` 후 `seek()`                            | 준비 전 `seek` 이 사라지거나 이전 영상에 적용된다. 보류 큐를 하나 더 만들어야 한다 |
| `position()` 이 준비 전 `0` 을 반환             | "맨 앞" 과 "모른다" 가 구분되지 않는다. 0초 Moment 가 생긴다                       |
| 시점을 **저장 버튼을 누를 때가 아니라** 저장 시 | 메모를 쓰는 동안 흘러간 만큼 어긋난다                                              |
| 탐색 바 UI 를 우리가 그림                       | 네이티브 컨트롤을 가린다 (III.I.6). M3 결정을 뒤집을 이유가 없다                   |
| Moment 재생을 가시성 가드에서 제외              | 가려진 채 소리가 난다 (III.I.9). 예외 경로가 정책을 무의미하게 만든다              |

## 결과

- 계약이 여덟 개가 된다. 추가 둘은 **선택이 아니라 필수**이므로
  `FakePlayerAdapter` 도 구현한다 — 두 구현이 갈라지지 않게 하는 기존 방침.
- `PlayerLoadOptions` 에 선택 필드가 하나 는다. 기존 호출부는 그대로다.
- `PlaybackCoordinator` 가 다섯 번째 면을 얻는다. 기존 네 면은 바뀌지 않는다.
- Moment 재생이 가시성·실패·거절에서 **다른 재생과 완전히 같게** 동작한다.
  새 정책이 없으므로 새 구멍도 없다.
- `PlayerSurface` 와 iframe 은 전혀 바뀌지 않는다. `seek` 도 `startSeconds`
  도 **적재된 플레이어에 보내는 명령**이지 재생성이 아니다 (ADR 0002).

## 구현 기록 (M9-3, 2026-11-10)

결정 1~6 이 코드로 들어갔다. `PlayerAdapter` · `YouTubeIFramePlayerAdapter` ·
`FakePlayerAdapter` · `playbackCoordinator.ts` · `createPlaybackCoordinator.ts`.
구현하면서 **설계가 답하지 않았던 것**을 아래처럼 정했다.

### 7. `position()` 은 플레이어가 보고하는 영상이 마지막으로 적재한 영상일 때만 숫자다

IFrame API 는 사건에 적재 식별자를 주지 않는다 (ADR 0012 의 한계). 그래서
`loadVideoById(B)` 직후 `getCurrentTime()` 은 **A 의 값**일 수 있다. 어댑터는
`getVideoUrl()` 로 플레이어가 지금 어느 영상을 보고하는지 읽고, 자기가 마지막으로
적재를 명령한 영상과 다르면 `null` 을 준다. 두 값은 같은 캐시에서 나오므로
같은 순간에 읽으면 같은 영상의 값이다.

실측 (Chromium 155 headless, 실제 IFrame API): `loadVideoById(B)` 직후 캐시가
**비워져** `getVideoUrl()` 이 `undefined` 가 되고 → `position()` 은 `null`. 그
뒤 B 의 보고가 오면 숫자. 전환 창에서 A 의 위치가 B 의 것으로 나가는 길이 없다.

### 8. 같은 영상이라도 플레이어가 위치를 모르거나 오류면 `seek` 하지 않고 시점을 실어 다시 적재한다

준비 전의 `seek` 은 버려지고(결정 2 — 보류 큐를 두지 않는다) `play` 만 보류되어
**처음부터** 재생된다. 오류 상태의 플레이어에 보내는 `seek` 도 아무 일을 하지
않는다 (`togglePlay` 가 오류에서 다시 적재하는 것과 같은 사정). 두 경우는
`load(videoId, { autoplay: true, startSeconds })` 로 간다. 재적재가 일어나지만
그 플레이어에는 아직 재생 중인 것이 없으므로 끊기는 것도 없다.

### 9. 현재 큐 안의 영상이면 큐를 **유지**하고 자리만 옮긴다

M9-1 §4-2 는 라이브러리만 봤다 (선택 목록 → 다른 목록 → 단일 곡). 그대로 두면
듣고 있던 큐 안의 영상인데도 **선택 목록이 바뀌었다는 이유로 큐를 갈아치운다**
— 사용자가 듣던 순서가 예고 없이 바뀐다. 큐는 재생 시작 시점의 스냅샷이고 그
성질을 지킨다. 그래서 라이브러리를 보기 **전에** 현재 큐를 본다.

### 10. `seek` 뒤 재생이 시작되기 전의 `ENDED` 는 그 명령보다 오래된 신호다

끝나 가던 영상에서 시점을 되돌리는 순간, 끝 신호가 뒤늦게 도착할 수 있다. 그것을
믿으면 사용자가 고른 순간을 건너뛰고 다음 곡이 나온다. `load` 경로가 쓰는
`hasStartedPlaying` 규칙을 `seek` 경로에도 적용한다 — `PLAYING` 이 온 뒤의
`ENDED` 만 자동 전환한다.

### 11. `seek` 뒤에는 `play` 를 이어 보낸다

YouTube 의 `seekTo` 는 **일시정지 중이면 멈춘 채 남고**, 그 밖의 상태에서는
재생을 시작한다. 실측으로 확인했다 — paused 에서 `seekTo(10)` 뒤 상태 변화
없이 `paused` 유지, 위치만 10. Moment 재생은 "그 지점부터 **듣는다**" 이므로
`play()` 를 이어 보내 재생을 보장한다. 이미 재생 중이면 무해하다.

### 12. 첫 영상의 시점은 `start` 파라미터로 싣는다

플레이어가 아직 없을 때 들어온 `load(A, { startSeconds })` 는 생성자에 A 를
넘기므로 `loadVideoById` 를 쓸 수 없다. 공식 플레이어 파라미터 `start`(정수)를
쓴다. `onReady` 뒤 `seekTo` 로 옮기는 대안은 cued 상태의 플레이어를 **재생시켜
버린다** (결정 11 의 동작) — 대기(autoplay 없음)로 적재한 영상이 혼자 재생된다.
실측: `start: 12` 로 만든 플레이어가 ready 시점에 `getCurrentTime() = 12` 를
보고하고, `playVideo()` 뒤 12 초부터 재생됐다.

### 13. `playMoment` 의 결과는 `PlayRequestResult` 의 **상위 집합**이다

설계는 `PlayRequestResult` 를 그대로 쓰기로 했다. 구현하면서 둘이 더 필요했다 —
`invalid-moment`(저장소에서 온 값도 믿지 않는다)와 `player-unavailable`(명령을
받을 플레이어가 없으면 **성공으로 돌려주지 않는다**). 기존 유니온에 더하면 세
UI 의 `Record<PlayRequestFailure, string>` 이 받을 수 없는 이유의 문구를 들고
있어야 한다. 그래서 `MomentPlayFailure = PlayRequestFailure | …` 로 **포함**만
한다. `player-hidden` 은 같은 값이라 UI 가 같은 문구를 쓴다.

> `playPlaylist` · `playTrack` 은 어댑터가 없어도 `ok: true` 를 돌려준다
> (M3-2 부터). 앱에서는 `PlayerSurface` 가 항상 어댑터를 등록하므로 닿지 않는
> 경로다. M9-3 은 그 둘을 바꾸지 않았다 — 바꾸면 세 UI 의 문구 표가 함께
> 바뀌어야 하고, 이번 범위가 아니다. **TODO** 로 남긴다.

### 14. `MomentTarget.title`

라이브러리 어디에도 없는 영상을 **단일 곡**으로 재생할 때 데크에 보일 이름이
필요하다. 설계의 `{ videoId, atSeconds }` 에 선택 `title` 을 더했다 — Moment 의
스냅샷 제목이다. 라이브러리에 있으면 그쪽 제목이 쓰이므로 무시되고, 없으면
트랙과 같은 대체 표기 `YouTube · <videoId>` 다.

| 확인한 것                                             | 결과                                                     |
| ----------------------------------------------------- | -------------------------------------------------------- |
| 준비 전 `position()`                                  | `null`. ready 직후 cued 영상은 `0` (`null` 과 구분됨)    |
| 재생 중 `getCurrentTime()`                            | 소수 (`1.775084…`) — 어댑터가 그대로 전함                |
| `seek(14)` (재생 중)                                  | 30ms 뒤 BUFFERING(14.0) → PLAYING(14.08). 재적재 없음    |
| `seek(10)` (일시정지 중)                              | 상태 변화 없이 `paused` 유지, 위치 10 → `play()` 로 재생 |
| `load(B, { startSeconds: 60 })`                       | 직후 `position()=null` → B 보고 → **60.06 에서 PLAYING** |
| 첫 `load(A, { startSeconds: 12 })` (`start` 파라미터) | ready 에 12 보고, `playVideo()` 뒤 12.03 에서 PLAYING    |
| `seek(NaN)` · `seek(-5)`                              | `seekTo` 미호출. 재생이 흔들리지 않음 (62.0 → 62.6)      |
| iframe                                                | 전 과정에서 `YT.Player` 1개, iframe 1개                  |

**실제 `PLAYING` 을 관측했다.** 다만 `--autoplay-policy=no-user-gesture-required`
와 `--mute-audio` 를 준 헤드리스다. 운영 사이트의 자동재생 정책에서는 사용자
제스처가 필요하고, Moment 누름은 제스처이므로 보통 닿지 않는다. 운영 사이트에서는
검증하지 않았다 (배포하지 않았다).

하나 더 보였다 — `loadVideoById({ startSeconds })` 와 `start` 파라미터 모두,
플레이어가 새 영상을 **`0` 으로 한 번 보고한 뒤**(~200ms) 지정 시점으로 간다.
그 창에서 `position()` 은 영상은 맞고 시간만 `0` 인 값을 준다. 이전 영상의 값은
아니므로 결정 7 의 보호 대상이 아니고, 사람이 200ms 안에 저장 버튼을 누를 수는
없다. **M9-4 가 저장 버튼을 만들 때 `playing` 이후에만 활성화하는 것을 검토한다**
(아래 TODO).

**M9-4 추가 (ADR 0021 결정 3)**: `capturePosition()` 은 `playback.isPositionReliable`
(마지막 명령 이후 실제 재생 시작)이 아니면 `null` 이다. 위 "하나 더 보였다" 의
