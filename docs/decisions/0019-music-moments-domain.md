# 0019. Moment 는 영상을 가리키고 자기 저장 키에 담긴다

- 상태: 채택 (설계)
- 날짜: 2026-11-07
- 관련: `docs/product/MUSIC_MOMENTS.md`,
  `docs/architecture/MOMENTS_DESIGN.md`,
  `docs/architecture/BACKUP_FORMAT.md` §6,
  **ADR 0007** (라이브러리 데이터 보호), **ADR 0018** (JSON 백업·복원),
  **ADR 0020** (재생 시점 조회와 이동)

## 배경

M9 는 "듣다가 마음에 든 순간"을 타임스탬프와 메모로 남기고 다시 찾아가게
한다. 설계에서 먼저 답해야 하는 것은 **Moment 가 무엇을 가리키는가**와
**어디에 저장되는가**다. 이 둘이 나머지(백업·확장·삭제 동작)를 전부 결정한다.

지시서의 요구가 하나 못 박혀 있다. **트랙이 삭제돼도 Moment 는 남아야 한다.**

## 결정

### 1. Moment 는 `track.id` 가 아니라 `videoId` 를 가리킨다

```ts
interface Moment {
  id: string // 앱 내부 식별자
  source: 'youtube'
  videoId: string // 11자. 이것이 유일한 외부 참조다
  atSeconds: number // 영상 시작점부터의 초. 0 이상 정수
  note: string // 사용자 메모. 빈 문자열 허용
  title: string // 저장 당시 보이던 제목 (스냅샷)
  createdAt: string // ISO 8601 UTC
  updatedAt: string // ISO 8601 UTC
}
```

`track.id` 는 **앱 내부 식별자이고, 같은 영상이 여러 트랙으로 존재할 수
있다** (`SYSTEM_DESIGN.md` §7.2). 트랙을 가리키면 트랙을 지우는 순간 Moment
가 끊어진 참조가 된다 — 지시서가 금지한 바로 그 상태다.

`videoId` 를 가리키면 Moment 는 **라이브러리와 독립한 사실**이 된다. "이
영상의 1분 23초" 는 플레이리스트가 어떻게 바뀌어도 참이다.

이것은 백업 설계가 M8-1 에서 이미 **권고**한 것이다
(`BACKUP_FORMAT.md` §6-2). M9 에서 결정으로 올린다.

### 2. 제목은 스냅샷으로 저장하되, 살아 있으면 현재 제목을 보여준다

제목을 저장하지 않으면 트랙이 지워진 Moment 는 `jNQXAC9IVRw` 같은 11자
문자열로만 남는다. 사용자는 그게 무엇이었는지 알 수 없다 — 지시서의 "트랙이
삭제되더라도 유지" 가 형식만 남고 쓸모를 잃는다.

제목만 저장하고 라이브러리를 보지 않으면, 트랙 이름을 바꿔도 Moment 는 옛
이름을 들고 있다 (M6-5 가 이름 변경을 넣었다).

**둘 다 한다.**

| 상황                                | 보여주는 것                |
| ----------------------------------- | -------------------------- |
| 같은 `videoId` 가 라이브러리에 있음 | 라이브러리의 **현재** 제목 |
| 라이브러리에 없음                   | 저장 당시 **스냅샷** 제목  |
| 스냅샷도 비어 있음                  | `YouTube · <videoId>`      |

마지막 줄은 `addTrack`·`renameTrack` 이 쓰는 `normalizeTitle` 의 대체 표기와
**같은 규칙**이다. 새 규칙을 만들지 않는다.

조회는 **표시 시점의 파생값**이고 저장하지 않는다. 저장하면 라이브러리를
고칠 때마다 Moment 를 다시 써야 하고, 그러면 두 키가 서로를 쓰게 된다.

### 3. 저장 키를 새로 둔다 — `39page.moments`

```
키: 39page.moments
{ "version": 1, "data": [ { ... }, ... ] }
```

라이브러리 키에 넣지 않는 이유가 셋이다.

1. **라이브러리 교체가 Moment 를 지우면 안 된다.** M8-3 의 가져오기는 전체
   교체다. 같은 키에 있으면 백업 복원이 Moment 를 통째로 날린다.
2. **M8 이전 빌드와의 사고를 막는다.** 키가 다르면, 캐시된 옛 빌드가 백업을
   가져와 `39page.library` 를 덮어써도 `39page.moments` 는 **건드려지지
   않는다.** 옛 빌드는 그 키의 존재를 모른다.
3. **쓰기를 분리한다는 기존 원칙** 그대로다 — 테마를 바꿔도 라이브러리를
   쓰지 않는다 (`SYSTEM_DESIGN.md` §7, `keys.ts` 주석).

`STORAGE_KEYS` 에 항목을 **더할 뿐** 기존 두 키의 이름·봉투·쓰기 경로는
바꾸지 않는다.

ADR 0007 의 보호가 그대로 적용된다 — 읽지 못한 `39page.moments` 원본은
덮어쓰지 않고 보호 상태로 둔다.

### 4. 섹션 간 참조 정합성을 조건으로 두지 않는다

Moment 가 가리키는 영상이 라이브러리에 없어도 **그 Moment 는 유효하다.**
가져오기가 "라이브러리에 없는 영상의 Moment" 를 버리지 않는다.

버리면 두 가지가 동시에 깨진다. 트랙 삭제 후 유지 요구가 깨지고, 두 섹션의
버전을 독립적으로 올릴 수 없게 된다 (`BACKUP_FORMAT.md` §6-2).

### 5. 순서는 저장하지 않는다

배열에는 **추가된 순서**로 쌓고, 정렬은 화면이 한다. 기본 보기는 영상별로
묶고, 영상은 가장 최근 Moment 순, 영상 안에서는 `atSeconds` 오름차순이다.

트랙 순서와 다르게 다루는 이유: 트랙 순서는 **사용자가 정한 값**이라 저장
대상이지만, Moment 의 나열 순서는 보기 방식일 뿐이다. 저장하면 정렬을 바꿀
때마다 사용자 데이터를 다시 쓰게 된다.

### 6. 개수 상한을 두지 않는다

Moment 하나는 200바이트 안팎이다. M8-4 실측에서 `localStorage` 는 5.12 MB
를 받아냈다 — 2만 개를 넘겨야 닿는 크기다.

상한을 두면 **저장을 조용히 거절하는 경로**가 생긴다. 대신 용량이 실제로
모자라면 기존 쓰기 실패 경로(`quota-exceeded`)가 잡고, M8-4 가 만든 "저장
되지 않음" 안내가 그대로 뜬다. 이미 있는 정직한 실패를 쓴다.

### 7. 메모 길이 상한은 500자, 제목 스냅샷은 100자 — M9-2 에서 확정

M9-1 이 **정하지 않았다.** `MOMENTS_DESIGN.md` §2 의 검증 표는 `note` 와
`title` 이 "문자열인지" 만 물었다. M9-2 가 store 를 만들면서 정해야 했다.

| 값                        | 상한 | 근거                                                |
| ------------------------- | ---- | --------------------------------------------------- |
| `MAX_MOMENT_NOTE_LENGTH`  | 500  | 메모는 문장이다. 제목보다 길어야 한다               |
| `MAX_MOMENT_TITLE_LENGTH` | 100  | `MAX_TRACK_TITLE_LENGTH` 와 같은 값. 같은 성격의 값 |

500자를 고른 이유는 용량이다. 최대 길이 메모 하나는 봉투까지 합쳐 1 KB
안팎이고, M8-4 가 실측한 `localStorage` 5.12 MB 기준으로 **그런 Moment
5000개**가 들어간다. 상한이 없으면 한 건이 저장소를 다 쓸 수 있다.

`MAX_MOMENT_TITLE_LENGTH` 는 라이브러리에서 **import 하지 않는다.** 두
store 를 독립적으로 두기 위해서다 (`AGENTS.md` 규칙 2). 두 값이 갈라지지
않게 하는 것은 테스트다 (`moments-store.spec.ts` — 두 상수를 비교한다).

**상한은 입력에만 적용된다.** 이미 저장된 긴 메모를 읽을 때는 길이를 보지
않는다. 읽는 자리에서 자르거나 버리면 사용자 데이터가 조용히 사라진다 —
어디서 왔든 이미 저장된 것은 사용자의 것이다.

### 8. 빈 제목 스냅샷을 대체 표기로 채우지 않는다 — M9-2 에서 확정

`addTrack` 의 `normalizeTitle` 은 빈 제목을 `YouTube · <videoId>` 로 채운다.
Moment 의 스냅샷은 **채우지 않는다.**

결정 2 의 표시 우선순위가 3단계이기 때문이다 — 라이브러리의 현재 제목 →
스냅샷 → `YouTube · <videoId>`. 저장 시점에 3단계 표기를 채워 넣으면
"스냅샷이 없다" 와 "스냅샷이 대체 표기다" 가 구별되지 않고, 2단계와 3단계가
같아진다. 빈 문자열이 "저장 당시 제목을 몰랐다" 를 뜻한다.

3단계 표기를 실제로 붙이는 것은 **표시 계층(M9-4)** 의 일이다.

### 9. 날짜는 문자열인지만 검증한다 — M9-2 에서 확정

`createdAt` · `updatedAt` 을 파싱해서 거부하지 않는다. 해석하지 못하는
타임스탬프 하나 때문에 Moment 전체를 버리면 **메모와 시점까지 함께 잃는다.**
사용자에게 값있는 부분은 그 둘이다.

쓰는 쪽은 항상 `Date#toISOString()` 을 쓰므로, 해석할 수 없는 날짜는 우리가
쓴 값이 아니다. 그래도 버리지 않는다 — 버려서 얻는 것이 없다.

## 대안

| 후보                                     | 탈락 이유                                                                                 |
| ---------------------------------------- | ----------------------------------------------------------------------------------------- |
| **`videoId` 참조 + 전용 키** (채택)      | 위                                                                                        |
| `track.id` 참조                          | 트랙 삭제가 Moment 를 끊는다. 지시서가 금지했다                                           |
| `track.id` 참조 + 삭제 시 Moment 도 삭제 | 사용자 데이터를 자동 삭제한다. 상시 제약 위반                                             |
| 라이브러리 키 안에 `moments` 필드로 넣기 | 백업 복원이 Moment 를 날린다. 옛 빌드가 모르는 필드를 떨어뜨린다                          |
| 플레이리스트별 Moment                    | 같은 영상이 두 목록에 있으면 Moment 가 갈린다. "이 영상의 그 순간" 이라는 사실과 어긋난다 |
| 제목을 저장하지 않음                     | 트랙이 지워지면 11자 ID 만 남아 쓸모가 없다                                               |
| 제목을 저장하고 라이브러리를 보지 않음   | 트랙 이름을 바꿔도 Moment 는 옛 이름을 들고 있다 (M6-5 와 어긋난다)                       |
| `atSeconds` 를 소수로 저장               | 거짓 정밀도다. 음악에서 1초 미만은 사용자가 지정할 수도 확인할 수도 없고 파일만 커진다    |
| 개수 상한                                | 조용히 거절하는 경로가 생긴다. 실제 한계는 쓰기 실패가 이미 잡는다                        |
| 메모 길이 무제한                         | 한 건이 저장소를 다 쓸 수 있다. 상한 없이 거절하면 이유를 말할 수 없다                    |
| 저장된 긴 메모를 읽을 때 자름            | 사용자 데이터가 조용히 짧아진다. 읽기는 쓰지 않는다는 보장과도 어긋난다                   |
| 빈 제목 스냅샷을 대체 표기로 채움        | 표시 2단계와 3단계가 구별되지 않는다 (결정 8)                                             |
| 날짜를 파싱해 거부                       | 타임스탬프 하나 때문에 메모와 시점까지 잃는다 (결정 9)                                    |

## 결과

- 트랙·플레이리스트를 지워도 Moment 가 남는다. **지시서 요구가 구조로
  보장된다** — 지우는 코드가 Moment 를 모른다.
- 백업 복원이 Moment 를 건드리지 않는다. 섹션이 **있을 때만** 교체한다
  (`BACKUP_FORMAT.md` §6, ADR 0018 의 "전체 교체" 는 라이브러리 섹션에만
  적용된다).
- 캐시된 옛 빌드가 백업을 복원해도 그 브라우저의 Moment 는 살아남는다.
  남는 위험은 **파일 계보**뿐이다 — 옛 빌드에서 새로 내보낸 파일에는
  Moment 가 없다. 이것은 코드로 막을 수 없으므로 문서와 안내로 다룬다
  (`MOMENTS_DESIGN.md` §5-3).
- `STORAGE_KEYS` 가 셋이 된다. 기존 둘은 그대로다.
- M10 확장이 만들 Moment 도 같은 모양이다 — 앱 내부 식별자를 참조하지
  않으므로 YouTube 페이지에서 만든 것이 그대로 유효하다 (**ADR 0020** §6).

## 구현 상태 (M9-2, 2026-11-07)

결정 1~9 가 **코드로 들어갔다.** `src/shared/types/moments.ts` ·
`src/stores/moments.ts` · `STORAGE_KEYS.moments`.

- 결정 1·3 (트랙 삭제에도 남는다)은 `moments-library-isolation.spec.ts` 가
  **동작으로** 확인한다 — 트랙 삭제 · 플레이리스트 삭제 ·
  `library.replaceAll` · 새로고침 네 경로 전부
- 결정 2 의 표시 3단계 중 **1·3단계는 아직 없다.** M9-2 는 스냅샷만 저장한다
  (표시는 M9-4)
- 결정 6 (개수 상한 없음)은 그대로다. 메모 길이 상한만 생겼다 (결정 7)

**아직 앱에 연결되지 않았다.** `main.ts` 는 Moments 를 복원하지 않고, 어떤
컴포넌트도 이 store 를 부르지 않는다. 프로덕션 번들에서 **tree-shaking 으로
빠져 있다** — 실측으로 확인했다. 연결은 UI 가 생기는 M9-4 에서 한다.
