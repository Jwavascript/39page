# 0034. 앨범아트를 포함한 전체 백업 · 파일 공유는 ZIP 패키지로 하고, 기존 JSON 백업을 그 안에 그대로 넣는다

- 상태: **채택 — M12-1 설계 (2026-11-15)** · 구현 M12-4 · **파일 공유 부분은 대체됨 — [ADR 0043](0043-share-dialog-and-backup-only-data-dialog.md)
  (2026-11-20, 파일 공유를 없앴다. 전체 백업 ZIP 은 그대로)**
- 관련: ADR 0018 (JSON 백업) · 0033 (Artwork 저장), `docs/architecture/ARTWORK_DESIGN.md` §7 · §8

## 배경

M12-6: 구도 이식을 위해 ZIP·공유 manifest 및 Artwork/공유 JSON을 v2로 내보내며 v1/v2를 읽는다.
내부 `backup.json`은 기존 형식이다. [ADR 0035](0035-m12-6-edit-sessions-and-artwork-display.md) 결정 8 참조.

사용자 이미지는 IndexedDB 에만 있다. JSON 백업(ADR 0018)만으로는 다른 컴퓨터에서 Artwork 를 복원할 수 없다. 서버 · 계정이 없으므로
공유도 파일로 한다.

## 결정

1. **전체 백업 = ZIP** (`manifest.json` · `backup.json` · `artwork.json` · `assets/<sha256>.<ext>`). `backup.json` 은 **기존 JSON 백업 파일
   그대로**다 — 검증기 · 미리보기 · 섹션별 쓰기를 다시 쓰고, 옛 빌드도 그 파일만 꺼내 가져올 수 있다.
2. 기존 JSON 내보내기는 "JSON 백업 (앨범아트 제외)" 로 남기고, 사용자 이미지가 있으면 빠진다고 알린다. Artwork 를 빠뜨린 파일을
   "전체 백업 완료" 라고 하지 않는다.
3. **복원은 검증 → 미리보기 → 스테이징(자산 추가만) → 텍스트 확정(기존 경로) → 연결 확정(한 트랜잭션) → 정리 · 확인**. 두 저장소를
   원자적이라고 하지 않고, 되돌릴 수 없는 지점(텍스트 확정) 전에 "지금 데이터 먼저 받기" 를 권한다.
4. 읽기 보안: 경로 허용 목록, 항목 수 · 선언 크기 · 실제 크기 · 압축률 한도, 중복 경로 · 자산, SHA-256 무결성, 이미지 재검증,
   미래 형식 버전 거절. 풀어 낸 파일을 HTML 로 해석하지 않는다 (JSON 은 `JSON.parse`, 이미지는 `<img>` 의 `blob:`).
5. **공유 패키지**(`39page-share`)는 고른 곡 · 목록과 그 그림만, Moments 는 사용자가 켰을 때 그 영상들의 것만 넣는다. 받는 쪽은 새
   id 를 만들고 보낸 쪽 id 는 `sourceId` 로만 둔다 (장래 커뮤니티 공유의 안정 식별자).
6. **ZIP 라이브러리: `fflate`** (런타임 의존성 추가 — AGENTS 규칙 8 검토 아래).

### 라이브러리 검토 (규칙 8)

- (a) 필요성: ZIP 읽기 · 쓰기(deflate 포함)는 표준 형식이지만 직접 구현하면 CRC · deflate · 중앙 디렉터리 · ZIP64 · 경계 검사를 새로
  짜야 하고, 지시서가 "자체 ZIP 포맷을 임의로 만들지 말라" 고 했다. 손으로 짠 파서는 보안 검사의 바탕으로 믿기 어렵다.
- (b) 기존 의존성 · 직접 구현: 런타임 의존성은 `vue` · `pinia` 뿐. 브라우저 `CompressionStream('deflate-raw')` 로 압축은 되지만 ZIP 구조
  읽기 · 쓰기는 직접 짜야 한다 — 위 이유로 택하지 않았다.
- (c) 후보:

  | 후보               | 크기 (gzip, 쓰는 부분)      | 유지          | 비고                                                                        |
  | ------------------ | --------------------------- | ------------- | --------------------------------------------------------------------------- |
  | **fflate 0.8.x**   | 약 8 ~ 12 KB (zip/unzip 만) | MIT, 의존성 0 | 동기 · 비동기 API, 항목별 `filter`(선언 크기를 보고 풀지 않기), 트리 셰이킹 |
  | JSZip 3.x          | 약 30 KB                    | MIT/GPL 이중  | Promise API, 오래된 코드 · 폴리필 포함, 크기 한도 훅이 약함                 |
  | @zip.js/zip.js 2.x | 수십 KB                     | BSD           | 스트리밍 · 암호화 등 기능이 많고 패키지가 크다 (8.7 MB)                     |

  fflate 를 고른다: 가장 작고 의존성이 없으며, 항목별 선언 크기를 먼저 보고 거를 수 있다. 정확한 버전으로 고정한다
  (**`fflate@0.8.2`**, 2024-02 — 널리 쓰이는 안정판. 0.8.3 은 2026-05 판).

- 실제 사용(M12-4): 읽기는 `Unzip` + `UnzipInflate` **스트리밍**으로 풀며 실제 바이트를 센다 — 머리말의 선언 크기는 거짓일 수
  있으므로 `unzipSync` 의 선언 크기에 기대지 않는다. 끝의 중앙 디렉터리 레코드가 없으면(잘린 파일) 손상으로 본다. 다른 realm 의
  `Uint8Array`(jsdom 시험의 `TextEncoder`)는 fflate 가 폴더로 오인하므로 넣기 전에 이 realm 으로 옮긴다 (같은 realm 이면 복사 없음).

- 개발 의존성 `fake-indexeddb` (Apache-2.0, 의존성 0): jsdom 에 IndexedDB 가 없다. 저장 계층의 트랜잭션 · 충돌 · 취소 시험에 쓴다.
  대안(인터페이스만 시험하는 메모리 가짜)은 실제 트랜잭션 의미를 확인하지 못해 택하지 않았다. 앱 번들에는 들어가지 않는다.

## 결과

- 백업 파일이 둘이 된다 (ZIP 권장 · JSON). 데이터 대화상자 문구로 차이를 설명한다.
- ZIP 복원 중 텍스트 확정 뒤 연결 확정이 실패하면 "곡은 복원됨 · 앨범아트 연결 다시 시도" 상태가 생길 수 있다 — 숨기지 않고 보고한다.
- 확인 (M12-4): 시험 — ZIP 보안 10 · 전체 백업 왕복 · 변조 · 실패 복구 11 · 공유 9. 실제 Chrome 7/7 — 프로필 A 에서 만든 ZIP 을 **새
  임시 프로필 B** 에 복원(목록 · 순서 · Moments · PNG · GIF · 연결 · 선택 목록), 변조한 ZIP 거절, 공유 파일을 **프로필 C** 에 새 목록으로
  (`docs/development/m12-results/real-chrome-transfer-m12-4.json`). 번들: 메인 JS gzip 71 KB → 76 KB 안팎 (M12-5 에서 측정).
