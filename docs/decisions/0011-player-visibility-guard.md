# 0011. 가시성은 순수 측정으로 판정하고, 가리는 쪽이 미리 통지한다

- 상태: 채택 (2026-11-04 일부 개정 — 노출 비율 임계값 폐지)
- 날짜: 2026-11-03

## 배경

YouTube 임베드는 충분히 보여야 한다. 근거가 둘로 나뉜다
(`../architecture/SYSTEM_DESIGN.md` §8.1).

- **200×200 은 공식 요구사항**이다. 바꿀 수 없다.
- **노출 비율 임계값은 우리 휴리스틱**이다. 개발자 정책에 수치 기준은 없고,
  금지된 것은 "사용자가 보고 있지 않은 곳에서의 재생"(III.I.9)이다.

구조상 어려운 점이 셋 있었다.

1. **측정 대상을 누가 소유하는가.** 영상 영역(`.player-mount`)은
   `PlayerSurface` 가 소유하고, 그 안쪽은 어댑터가 소유한다 (ADR 0002).
   코디네이터는 DOM 을 몰라야 하고, store 에는 노드를 넣을 수 없다 (ADR 0006).
2. **가려지는 순간을 어떻게 아는가.** 좁은 화면에서 드로어를 열면
   `DashboardShell` 의 CSS 가 스테이지를 `display: none` 으로 만든다. 관찰자는
   비동기라 그 사실을 **한 프레임 뒤에** 알려준다. 그동안 가려진 채로 소리가
   난다 — 정확히 III.I.9 가 금지하는 상태다.
3. **jsdom 에는 레이아웃이 없다.** 모든 `getBoundingClientRect()` 가 0 이고
   `matchMedia` 와 `IntersectionObserver` 가 아예 없다. 측정을 DOM 에 묶어두면
   가시성 정책을 단위 테스트로 검증할 수 없다.

## 결정

**판정은 순수 함수, 통지는 세 경로**로 나눈다.

### 1. 판정 — `measurePlayerVisibility(rect, viewport)`

사각형과 뷰포트 크기만 받는 순수 함수다 (`src/features/playback/playerVisibility.ts`).
프로토타입 `syncVisibility()` 와 같은 계산이고, 공식 요구와 휴리스틱을 상수로
갈라 둔다.

```
면적 0            → covered    (display: none)
200×200 미만      → too-small  (공식 요구 위반)
노출 비율 ≤ 0.5   → covered    (우리 휴리스틱)
그 밖             → ok
```

`display: none` 을 `too-small` 이 아니라 `covered` 로 보는 이유: 문구가 갈린다.
창을 키우라고 안내하면 사용자가 할 수 있는 일이 없다.

### 2. 측정 등록 — `attachAdapter(adapter, visibility?)`

영역을 소유한 `PlayerSurface` 가 **함수 하나**를 어댑터와 함께 등록한다.
코디네이터는 그 함수만 들고 있으므로 DOM 을 모른 채 판정할 수 있다.
등록되지 않으면 판정하지 않는다 — 영역이 없으면 가려질 것도 없다.

### 3. 재평가 통지 — 셋

| 경로                           | 담당             | 시점                    |
| ------------------------------ | ---------------- | ----------------------- |
| 재생을 **시작하기 직전** 측정  | 코디네이터       | 모든 시작 경로          |
| `revalidatePlayerVisibility()` | `PlayerSurface`  | 관찰자·`resize` 가 알림 |
| `playerWillHide()`             | `DashboardShell` | 드로어를 **열기 직전**  |

`playerWillHide()` 가 따로 필요한 이유: 그 시점에는 플레이어가 **아직 보인다.**
측정에 맡기면 "보인다" 가 나와 멈추지 않고, 가려진 뒤에 관찰자가 알려주는
사이에 소리가 난다. 그래서 이 통지는 **측정하지 않고 그대로 멈춘다.**

### 4. 관찰 수단 — `IntersectionObserver` + `resize`

`IntersectionObserver` 가 스크롤·뷰포트 변화·`display: none` 을 폴링 없이
알려준다. 다만 **얼마나 보이는가는 관찰자의 값을 쓰지 않고** `measure()` 가
그때 다시 읽는다. 판정 경로가 하나여야 테스트가 전수 검증한 것과 실제 동작이
같아진다.

`resize` 를 함께 듣는 것은 관찰자가 없는 환경의 최소 보장이다. 관찰자가 없을
때만 `scroll` 까지 듣는다 — 있으면 중복이다.

### 5. 화면 밖이면 한 번 끌어와 본다

재생을 시작하기 전 측정이 `covered` 로 나오면 **영역을 화면 안으로 끌어온 뒤
다시 잰다** (`scrollIntoView({ behavior: 'instant', block: 'center' })`).

왜 필요한가 — 브라우저 검증에서 드러났다. 1100px 이하에서는 레이아웃이 단일
열이 되고, 승인된 레퍼런스와 같은 순서(데크 · 마스코트 · 시계 · 날씨 ·
플레이어)에서 플레이어는 **화면 한참 아래**에 놓인다. 1000×713 실측으로
`.player-mount` 의 top 이 **1247px** 였다. 즉 페이지 상단에서 ▶ 를 누르면
가시성 가드가 항상 거절한다. 끌어오지 않으면 좁은 화면에서 **아무것도 재생할
수 없다.**

조건을 셋 달았다.

- **보이면 끌어오지 않는다.** 재생할 때마다 화면이 멋대로 움직이면 안 된다.
- **`too-small` 에는 끌어오지 않는다.** 스크롤로 해결되는 문제가 아니다.
- **끌어와도 안 보이면 거절한다.** 드로어가 덮은 `display: none` 은 스크롤로
  드러나지 않는다. 재측정이 다시 거절한다.

정책적으로도 이쪽이 맞다. III.I.9 가 금지하는 것은 "보이지 않는 곳에서의
재생" 이다. 가려진 채로 재생하는 것보다 **보이게 만드는 것**이 그 조항에
부합한다.

### 6. 거절 안내는 두 곳에서

재생 요청이 가시성 때문에 거절되면 `{ ok: false, reason: 'player-hidden' }` 을
돌려주고 **큐를 바꾸지 않는다.**

- 플레이어의 `.status` 영역: 일반 안내 (코디네이터)
- 드로어의 `.play-notice`: "닫고 ▶ 를 눌러주세요" (드로어)

드로어가 따로 안내하는 이유: 좁은 화면에서는 드로어가 스테이지를 **대체**하므로
`.status` 영역이 드로어와 함께 숨는다. 사용자가 누른 자리에 보여야 한다.

### 7. 복귀는 수동이다

가려져서 멈춘 뒤 다시 보이게 되어도 **자동으로 재생하지 않는다.** 사용자가
▶ 를 눌러야 한다. 보이게 됐다는 것만으로 소리를 내면 사용자가 의도하지 않은
재생이 된다. 프로토타입도 `pausedForDrawer` 를 기록만 하고 복귀에 쓰지 않는다.

## 대안

| 대안                                          | 왜 택하지 않았는가                                                                                                   |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 코디네이터가 DOM 을 직접 재다                 | 재생 로직이 DOM 과 레이아웃에 묶인다. jsdom 에서 정책을 검증할 수 없다                                               |
| 가시성 상태를 `playback` store 에 둔다        | 측정값은 파생값이고 매 프레임 바뀔 수 있다. store 에 넣으면 반응형 갱신이 레이아웃 읽기를 유발한다                   |
| 관찰자의 `intersectionRatio` 를 그대로 믿는다 | 200×200 검사를 따로 해야 하고, 판정이 두 경로로 갈린다. 테스트가 본 것과 실제 동작이 달라질 여지가 생긴다            |
| 재생 요청 시 드로어를 자동으로 닫는다         | 프로토타입은 그렇게 한다. 하지만 재생 쪽이 라이브러리 UI 를 조작하는 의존이 생긴다. 넓은 화면에서는 닫을 이유도 없다 |
| 가려진 동안 다음 곡으로 넘긴다                | M3-0.7 이 금지한다. 조용히 큐가 흐르면 사용자는 무엇이 왜 건너뛰어졌는지 모른다                                      |
| `matchMedia` 가 없으면 가려진 것으로 본다     | 없다는 이유로 멈추면 실제로 보이는 플레이어를 멈춘다. 실제 가려짐은 관찰자가 한 틱 뒤에 잡는다                       |

## 결과

- 가시성 정책이 **단위 테스트로 전수 검증된다.** 경계값(정확히 200×200, 정확히
  절반)까지 포함한다.
- `playback` store 와 `library` store 는 여전히 서로를 모르고, 둘 다 DOM 을
  모른다.
- `DashboardShell` 이 재생 계약의 **통지 하나**(`PlaybackVisibility`)를 알게
  됐다. 재생 상태를 읽거나 플레이어를 직접 부르지는 않는다.
- jsdom 에 레이아웃이 없으므로 통합 테스트는 사각형과 `matchMedia` 를 세워
  쓴다 (`tests/support/playerLayout.ts`). **실제 브레이크포인트 적용과 실제
  재생은 브라우저 검증에서만 확인된다.**
- 50% 임계값은 ADR 없이 조정할 수 있다. 200×200 과 "가려지면 멈춘다" 는
  조정 대상이 아니다.

## 개정 (2026-11-06, M7-1) — 가림을 측정이 본다

M6-2 는 "드로어와 플레이어가 **다른 그리드 셀**에 있다" 로 겹침을 막았다.
좁은 화면의 드로어가 **하단 시트**가 되면서 그 보장이 사라졌다.

처음에는 레이아웃으로 되살리려 했다 — 시트가 열린 동안 플레이어를
`position: sticky` 로 상단에 붙였다. **되돌렸다.** 짧은 화면에서는 남는 띠가
플레이어보다 얇아 보장이 성립하지 않고, 조상의 `overflow` 를 바꿔야 해서
레이아웃이 다른 이유로 깨질 수 있었다.

사용자 지시가 방향을 정했다: _"만약 유튜브 화면을 규정 이상으로 가리면 그냥
일시정지 하는 식으로 해줘."_

### 결정

**가리는 쪽이 높이를 알리고, 측정이 판정한다.**

```ts
// 계약 (PlaybackVisibility)
setBottomObstruction(px: number): void

// 측정 (순수 함수)
measurePlayerVisibility(rect, { width, height, obstructedBottom })
```

`DashboardShell` 이 시트의 **위쪽 테두리**를 재서 `window.innerHeight - top` 을
알린다. 높이를 직접 읽지 않는 이유: 시트가 화면 밖으로 조금 넘어가거나
안전 영역 여백이 붙으면 높이와 실제로 가리는 양이 달라진다.

재생 쪽은 **무엇이 가리는지 모른다.** 시트도 드로어도 브레이크포인트도 모르고
픽셀만 안다 (규칙 4).

### 판정선은 200×200 이다

| 가리는 것         | 기준                   | 왜                                       |
| ----------------- | ---------------------- | ---------------------------------------- |
| 뷰포트(스크롤)    | 조금이라도 보이면 허용 | 사용자가 스크롤 위치를 고른 것이다 (M6)  |
| **우리 오버레이** | **남은 높이가 200px**  | 앱이 영상을 덮어 놓고 소리를 내는 상태다 |

오버레이에 공식 숫자를 재사용한 것은 **새 임계값을 만들지 않기 위해서다.**
비율을 다시 들이면 M6 에서 폐지한 그 휴리스틱이 되살아난다. 요구사항이
"임베드 플레이어는 200×200 이상의 뷰포트를 가져야 한다" 이므로, 우리가 그
아래로 덮으면 요구사항을 우리 손으로 깬 것이다.

사유는 `too-small` 이 아니라 **`covered`** 다. 사용자가 할 일이 다르다 — 창을
키우는 것이 아니라 시트를 닫거나 영상이 보이는 곳으로 올리는 것이다.

### 함께 바뀐 것

- `reveal()` 의 `block` 이 `'center'` → `'start'` 가 됐다. 하단 시트가 열려
  있으면 화면 가운데는 시트 아래다 — 끌어온 결과가 다시 덮인 자리가 된다
- **거절 안내가 누른 자리로 돌아왔다.** M6-5 에서 "플레이어는 가려지지 않으니
  `.status` 하나면 된다" 고 지웠는데, 덮이면 그 안내도 함께 덮인다. 세 표면
  (시트 · 위젯 · 데크)이 `PLAY_REFUSED_HIDDEN_MESSAGE` 를 공유한다

넓은 화면의 보장은 그대로다. 우측 드로어가 정보 열 안에서 끝나므로 가림이
0 이고, `DashboardShell` 도 좁은 화면에서만 가림을 알린다.

## 개정 (2026-11-04, M6)

## 개정 (2026-11-04, M6) — 노출 비율 임계값을 폐지했다

실제 브라우저 검증에서 **"영상이 일부만 가려져도 음악이 멈춘다"** 가 보고됐다.
원인은 공식 정책이 아니라 위 결정의 `MIN_VISIBLE_FRACTION = 0.5` 였다.

판정선을 **"조금이라도 보이는가"** 하나로 바꿨다.

| 상태                      | 이전        | 지금      |
| ------------------------- | ----------- | --------- |
| 면적 0 (`display: none`)  | covered     | covered   |
| 200×200 미만              | too-small   | too-small |
| 뷰포트와 겹침 **0**       | covered     | covered   |
| 노출 50% 이하 (겹침 있음) | **covered** | **ok**    |

근거: III.I.9 가 금지하는 것은 "사용자가 보고 있지 않은 곳에서의 재생" 이다.
**부분적으로 가려진 플레이어는 사용자가 여전히 볼 수 있다.** 50% 라는 숫자는
개발자 정책에 없는 우리 휴리스틱이었고, 이 ADR 이 스스로 "조정할 수 있다" 고
적어 둔 항목이다. 따라서 새 ADR 을 만들지 않고 이 절로 개정한다.

바뀌지 않은 것:

- **200×200 은 그대로다.** 공식 요구사항이다.
- **완전히 보이지 않으면 그대로 멈춘다.** `display: none`, 뷰포트 완전 이탈,
  `playerWillHide()` 사전 통지 모두 유지한다.
- **복귀는 여전히 수동이다** (§7).

남은 한계: 측정은 **다른 요소에 덮인 경우를 알아내지 못한다.** 지금은 드로어를
형제 열로 둬서 "겹치지 않는다" 를 구조로 보장한다. **드로어를 오버레이로 바꾸는
M6 작업은 이 보장을 깨므로, 오버레이가 플레이어를 가리지 않도록 설계해야 한다**
(`../development/M6_PLAN.md` §4).

## 브라우저 실측 (2026-11-03, headless Chromium)

| 뷰포트   | 드로어 | `.player-mount` | 비고                                   |
| -------- | ------ | --------------- | -------------------------------------- |
| 1440×813 | 닫힘   | 536×301         | 공식 요구·권장 모두 충족               |
| 1440×813 | 열림   | **420×236**     | 요구(200×200) 충족, 권장(480×270) 미달 |
| 1000×713 | 닫힘   | 871×490         | top = **1247px** — 화면 밖             |
| 1000×713 | 열림   | **0×0**         | `display: none` — 재생 거절            |

1000px 에서 확인한 동작:

- 드로어 닫힘 + ▶ → `reveal()` 이 끌어와 재생이 시작된다 (iframe 생성됨)
- 드로어 열기 → `작은 화면에서는 영상이 가려져 일시정지됩니다.` (사전 통지)
- 드로어 안에서 ▶ → 드로어가 안내하고 **iframe 이 만들어지지 않는다**
- 스크롤로 밀려나면 `영상이 화면에서 가려져 일시정지됐어요.` (관찰자 경로)
- 테마 2회 · 드로어 2회 왕복 후 `iframes=1`, 같은 노드

**알려진 거친 부분**: 거절·중단 안내가 상황이 해소된 뒤에도 `.status` 에
남는다. 문구 정리는 M5 (`IMPLEMENTATION_PLAN.md` M5 5.5)에서 함께 다룬다.
