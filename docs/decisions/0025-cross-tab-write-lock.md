# 0025. 라이브러리·Moments 쓰기는 Web Locks 배타 잠금과 "수정 번호 영수증" 안에서 한다

- 상태: 채택 — **M10-3 안정화 (2026-11-11)**
- 관련: **ADR 0024** (기준 원문 비교 — 이 결정이 그 위에 선다), **ADR 0007** (데이터
  보호), **ADR 0018** (백업·복원), **ADR 0019** (Moments), **ADR 0023** (수집 화면)
- 구현: `src/shared/storage/crossTab.ts` (`createBaseline` · `createWriteGate`),
  `src/stores/library.ts`, `src/stores/moments.ts`

## 배경

ADR 0024 는 쓰기 직전에 저장소 원문을 기준과 비교한다. 그러나 `localStorage` 는
탭(렌더러)마다 사본을 두고 다른 탭의 쓰기를 **비동기로**(실측 6.5–23ms) 받는다. 두 탭이
서로의 쓰기를 받기 전에 각각 "비교 → 쓰기" 를 하면 둘 다 통과하고 나중에 도착한 쓰기가
앞의 것을 덮는다. M10-3C 실측에서 같은 순간(간격 0) 쓰기 20회 중 20회 한쪽을 잃었고,
감지(`possiblyOverwritten`)만 더했다.

Batch 3 지시: 협력하는 탭 사이에서 **조용한 데이터 손실이 없어야 한다.** 충돌은 정확히
알리고 안전한 재시도 경로를 둔다. 완전한 원자성을 제공하지 못하면 손실이 불가능하다고
주장하지 않는다.

ADR 0024 는 "Web Locks 로 쓰기 직렬화" 를 기각했다 — 잠금을 잡아도 앞 탭의 마지막 쓰기가
**이 렌더러에 도착했다는 보장이 없기** 때문이다. 이 결정은 그 빈틈을 메운다.

## 결정

### 1. 모든 쓰기 명령을 한 줄로 세운다 — 배타 잠금 `<키>:write`

라이브러리(`39page.library:write`)와 Moments(`39page.moments:write`)는 따로 잠근다 — 서로
다른 키이고, 한쪽이 붙잡혀도 다른 쪽은 쓴다.

잠금 안에서의 순서:

1. 잠금을 얻는다 (5초 한도, `AbortSignal`).
2. 앞 탭의 쓰기가 **이 탭에 보일 때까지** 기다린다 (아래 2번).
3. 명령 본문을 **await 없이 한 번에** 실행한다 — 기준 원문을 다시 보고(낡았으면 최신을
   다시 읽고 `conflict` 로 거절), 바꾸고, 쓰고, 쓴 원문을 기준으로 삼는다.
4. 썼으면 수정 번호를 올리고 영수증을 낸다.
5. 잠금을 놓는다.

잠금을 얻기 **전의** 메모리로 쓰지 않는다 — 본문의 첫 줄이 잠금 안에서 기준 원문을 다시
본다.

### 2. 영수증 — 잠금만으로 부족한 부분

쓴 탭은 별도 키 `<키>.rev` 의 수정 번호를 하나 올리고, 그 번호를 이름에 넣은 **공유
잠금** `<키>:rev:<번호>:<쓴 시각 ms>` 를 잡아 둔다 (탭마다 마지막 하나만 — 새 영수증을
잡으면 앞의 것을 놓는다).

다음 탭은 배타 잠금 안에서 `navigator.locks.query()` 로 걸린 영수증 중 가장 큰 번호를 보고,
**자기 저장소의 수정 번호가 그 이상이 될 때까지**(4ms 간격, 최대 1.5초) 기다린다.
잠금 관리자의 상태는 브라우저 전체에서 하나이고 잠금을 넘겨주기 전에 영수증이 걸려 있으므로,
다음 탭은 "앞 탭이 무엇을 썼는지" 를 저장소 전파와 상관없이 안다. 같은 렌더러의 쓰기는
순서대로 전달되므로 수정 번호가 보이면 그 앞의 데이터 쓰기도 보인다.

- 1.5초 안에 보이지 않으면 **쓰지 않는다** — 최신을 다시 읽고 `conflict`.
- 3초(`RECEIPT_EXPIRY_MS`)가 지난 영수증은 기다리지 않는다. 전파는 수십 ms 안에 끝나므로
  그때까지 번호가 안 보인다면 저장소가 비워졌거나(사이트 데이터 삭제) 쓰기가 사라진 것이다.
  그런 영수증 하나 때문에 모든 탭이 저장을 영영 거절하지 않게 한다. 번호는 만료된
  영수증까지 보고 매기므로 되돌아가지 않는다.
- 수정 번호를 쓰지 못하면(용량) 영수증도 내지 않는다.

`<키>.rev` 는 **사용자 데이터가 아니다.** 저장 봉투·스키마를 바꾸지 않고(ADR 0024 의 조건),
백업에 넣지 않는다. 없거나 망가지면 0 으로 본다.

### 3. 명령은 비동기다 — 저장이 끝난 뒤에만 성공을 말한다

store 의 쓰기 명령(`createPlaylist` … `renameTrack`, `seedFirstRunPlaylist`,
`replaceAll`, Moments 의 `add` · `addMoments` · `updateNote` · `remove` ·
`replaceAllMoments`)이 모두 `Promise` 를 돌려주고 **저장이 끝난 뒤** 이행한다.

- 화면은 기다리는 동안 버튼을 끄고(`aria-busy`) 다시 제출을 막는다 — 수집 화면 "저장 중…",
  드로어 양식, 새 목록, Moment 저장·메모 수정, 가져오기·다시 저장.
- 성공 안내는 이행된 결과로만 쓴다.
- 거절되면 입력(링크·메모)을 지우지 않는다. Moment 메모 수정 폼은 결과가 `true` 일 때만
  닫힌다 (`MomentList` 가 `saveNote` 함수를 받는다).

새 거절 이유:

| 이유       | 뜻                                                                | 화면                                   |
| ---------- | ----------------------------------------------------------------- | -------------------------------------- |
| `conflict` | 다른 탭이 먼저 바꿨다 (기준 비교 · 영수증 확인 실패). 다시 읽었다 | "최신을 불러왔어요 · 다시 해 주세요"   |
| `busy`     | 잠금을 5초 안에 얻지 못했거나 잠금 요청이 실패했다                | "다른 탭이 저장하는 중 · 잠시 뒤 다시" |
| `stale`    | (`replaceAll*` 전용) 잠금 안에서 본 원문이 승인 때와 다르다       | 가져오기의 "다시 확인" 안내            |

어느 경우도 **아무것도 쓰지 않았다.**

### 4. 같은 길 — 대시보드 · 수집 화면 · 가져오기

수집 화면(Quick Add, M10-4 Moment Capture 포함)은 대시보드와 같은 store 명령을 부르고,
가져오기는 `replaceAll(data, { expectedRaw })` · `replaceAllMoments(data, { expectedRaw })`
로 **잠금 안에서** 미리보기 때의 원문을 다시 본다. 미리 비교(ADR 0018)와 쓰기 사이에 다른
탭이 저장해도 덮지 않는다. 플레이리스트가 거절되면 아무것도 쓰지 않고, 플레이리스트를 쓴
뒤 Moments 가 거절되면 섹션 결과로 남긴다 (원자성은 여전히 없다 — ADR 0018 결정 9).

"다시 저장"(M8-4)도 같은 `expectedRaw` 로 잠금 안에서 확인한다. 실패 뒤 다른 탭이 저장했으면
다시 저장하지 않고 파일을 다시 고르게 한다.

화면·수집·가져오기 코드는 저장소에 직접 쓰지 않는다 — 원문 검사 테스트가 고정한다
(`tests/unit/cross-tab-locks.spec.ts`).

### 5. 보호 · 사용 불가 상태는 잠그지 않는다

`protected` · `unavailable` 의 평범한 수정은 저장하지 않으므로(ADR 0007) 잠그지 않고 바로
메모리에 반영한다. `replaceAll*` 만 상태와 관계없이 잠금을 지난다 (보호를 의도적으로 넘는
유일한 경로).

### 6. Web Locks 가 없으면 — 기준 원문 비교로 돌아간다

`navigator.locks` 가 없거나(구형 브라우저, 안전하지 않은 origin) 모양이 다르면 명령 본문을
**지금 바로** 실행하고 이미 이행된 결과를 돌려준다. ADR 0024 의 방어(비교 · 감지)가 그대로
남는다. 위험한 저장을 따로 거절하지는 않는다 — 거절하면 그 환경에서 저장이 아예 안 되고,
남는 창(아래 실측)은 사람이 닿기 어렵다. 대신 **잃으면 그 탭이 알린다**(M10-3C).

### 7. Moments 도 같은 정합성을 갖는다

ADR 0024 결정 9 의 TODO 를 닫는다. Moments store 에 기준 원문 비교 · `storage` 이벤트
반영(`watchExternalChanges`, 대시보드 `main.ts`) · 잠금 + 영수증을 같은 규약으로 더했다.

## 한계 — 막지 못하는 것

- **규약에 참여하지 않는 탭** — 이 변경 전 버전이 열려 있는 탭은 잠그지도 영수증을 내지도
  않는다. 그 탭과의 경합은 ADR 0024 수준(비교 · 감지)이다. 새로고침하면 참여한다.
- **Web Locks 가 없는 환경** — 같다.
- **쓰자마자(전파 전, 수 ms) 닫힌 탭** — 그 탭의 영수증이 잠금 관리자에서 사라진다. 그 순간
  다른 탭이 쓰면 비교만 남는다.
- **3초 넘게 전파되는 환경** — 영수증이 만료돼 비교만 남는다.
- `localStorage` 에 탭 간 트랜잭션은 없다. **데이터 손실이 불가능하다고 주장하지 않는다.**

## 실측

Chromium 155 헤드리스 · 격리 프로필 · 이 브랜치 웹앱 빌드를 `http://127.0.0.1:4173`(보안
컨텍스트, Web Locks 있음)로 띄웠다. 대시보드 두 탭을 **각각 다른 창**에 열어 둘 다 보이는
상태로 두고, 두 탭에 같은 절대 시각 T 와 T+간격을 예약해 store 명령을 실행했다. 예약은
타이머가 아니라 바쁜 대기로 맞췄다 — 처음 측정에서 백그라운드 탭의 타이머가 약 900ms
늦어져 "동시" 가 동시가 아니었고, 그 결과는 버렸다. 실제 간격 오차는 50회 모두 1ms 안.

**잠금 + 영수증 (이 결정)** — 유효한 실행 두 번의 합

| 경우                                                            | 시도 | 조용한 손실 | 결과                                                                       |
| --------------------------------------------------------------- | ---- | ----------- | -------------------------------------------------------------------------- |
| 라이브러리 — 같은 목록에 서로 다른 곡, 0·1·5·10·20ms            | 100  | **0**       | 100회 모두 두 곡 저장 (첫 시도에 둘 다 성공)                               |
| Moments — 서로 다른 Moment, 0·1·5ms                             | 60   | **0**       | 60회 모두 둘 다 저장                                                       |
| Moment 메모 수정 ↔ 같은 Moment 삭제 (0ms)                       | 12   | **0**       | 지운 것이 되살아나지 않음. 수정은 `not-found` 로 거절되거나 삭제 전에 저장 |
| 수집 화면 "플레이리스트에 추가"(실제 버튼) ↔ 대시보드 이름 변경 | 12   | **0**       | 곡과 새 이름이 둘 다 남음                                                  |
| 가져오기(`replaceAll`) ↔ 곡 추가                                | 12   | **0**       | 먼저 잠근 쪽만 반영 — 가져오기 `stale` 또는 추가 `not-found`(교체된 목록)  |
| 보호 상태 두 탭의 동시 수정                                     | 1    | —           | 원본 그대로, 둘 다 "저장되지 않음"                                         |

충돌(`conflict`)도 0 이었다. 두 번째 탭은 영수증 번호가 보이기를 기다리는 동안
`storage` 이벤트로 최신을 다시 읽었고, 명령이 그 위에서 실행됐다.

**잠금 · 실패 경로 (실제 브라우저)**

| 경우                                       | 결과                                                            |
| ------------------------------------------ | --------------------------------------------------------------- |
| 다른 탭이 쓰기 잠금을 붙잡고 놓지 않음     | 5008ms 뒤 `busy`, 저장소 그대로                                 |
| 붙잡은 탭을 0.8초 뒤 닫음                  | 기다리던 저장이 909ms 에 끝남 (닫힌 직후 풀림)                  |
| 붙잡은 탭을 0.8초 뒤 새로고침              | 948ms 에 끝남                                                   |
| 실제 용량 초과(1글자까지 채움) → 다시 시도 | 첫 저장 `quota-exceeded` · 비운 뒤 다시 시도는 **한 번만** 저장 |
| 영수증                                     | 키마다 탭당 하나 (`39page.library:rev:121:<ms>` 등)             |
| 쓰기 전파 시간                             | 3.1–10.3ms                                                      |

**같은 하네스에서 잠금을 끄면** (`navigator.locks` 를 숨긴 흉내)

| 경우                                  | 0ms   | 1ms   | 5ms   | 20ms  | 잃은 시도의 감지 표시 |
| ------------------------------------- | ----- | ----- | ----- | ----- | --------------------- |
| 두 탭 모두 잠금 없음                  | 10/10 | 10/10 | 10/10 | 10/10 | 40/40                 |
| 한 탭만 잠금 없음 (규약 밖의 탭 흉내) | 1/10  | 7/10  | 9/10  | 10/10 | 27/27                 |

이 하네스의 두 번째 탭은 T+간격까지 바쁜 대기로 메인 스레드가 막혀 있어 그동안 다른 탭의
쓰기를 받지 못한다 — **누르는 순간 사본이 낡은 탭**이다. 그래서 잠금이 없으면 20ms 간격에서도
잃는다 (M10-3C 의 다른 하네스에서는 5ms 이상에서 잃지 않았다). 같은 조건에서 잠금이 있으면
손실이 0 이다 — 영수증을 기다리는 동안 메인 스레드가 풀려 앞 쓰기를 받기 때문이다. 이 표가
"한계" 절의 근거다: 규약 밖의 탭과 Web Locks 없는 환경은 **막지 못하고 알리기만** 한다.

검증하지 못한 것: 서로 다른 브라우저 프로세스(프로필)·기기 사이 — 이 규약의 범위 밖이다
(같은 브라우저 프로필 안의 탭만 같은 `localStorage` 와 잠금 관리자를 공유한다).

## 대안

| 대안                                      | 기각 이유                                                                                   |
| ----------------------------------------- | ------------------------------------------------------------------------------------------- |
| 잠금만 (영수증 없이)                      | 잠금을 넘겨받은 탭이 앞 탭의 쓰기를 아직 받지 못했을 수 있다 (ADR 0024 의 기각 이유 그대로) |
| 데이터 봉투에 `revision` 필드             | 스키마·마이그레이션이 바뀐다. 별도 키로 같은 일을 한다                                      |
| 잠금 안에서 일정 시간(예: 50ms) 기다리기  | 전파 시간에 상한이 없다 — 늦으면 그대로 덮는다. 매 저장이 느려진다                          |
| 낡았으면 최신 위에 명령을 다시 적용(병합) | 삭제·이동처럼 사용자가 본 상태를 전제로 한 명령이 엉뚱하게 적용된다. 거절하고 다시 묻는다   |
| BroadcastChannel 리더 / IndexedDB         | ADR 0024 와 같은 이유 — 범위 밖                                                             |

## 결과

- 협력하는 탭(이 버전 · Web Locks 있음) 사이의 동시 쓰기는 한쪽이 거절되고 알린다 — 조용히
  덮지 않는다. 거절된 쪽은 다시 누르면 최신 위에 저장된다.
- 모든 쓰기 명령이 비동기가 됐다. 호출부·테스트가 결과를 기다린다.
- 잠금 대기 동안 버튼이 꺼진다. 평소 대기는 수 ms 다.
- 남은 위험은 위 "한계" 다.
