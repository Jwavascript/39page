# M6 — 실제 브라우저 검증 후속

> 상태: 착수 (1번 일부·3번 완료, 나머지 미착수)
>
> 출처: 2026-11-04 실제 브라우저 검증에서 사용자가 보고한 7건.
> 배포 이후 처음으로 실기기에서 확인한 결과다 (`DEPLOYMENT.md` §5).

MVP(M0–M5)는 jsdom 단위·통합 테스트와 headless Chromium 실측까지만 검증했다.
실제 브라우저·실기기에서 처음 드러난 문제를 여기서 다룬다.

## 1. 완료한 것 (2026-11-04)

### 1-a. 노출 비율 임계값 폐지 (보고 1번의 절반)

`MIN_VISIBLE_FRACTION = 0.5` 을 없애고 판정선을 **"조금이라도 보이는가"** 하나로
바꿨다. 상세와 근거는 ADR 0011 의 개정 절에 있다.

사용자가 물은 "정책상 그런 것이냐" 에 대한 답은 **아니다** 다. 200×200 은 공식
요구사항이지만 50% 는 우리가 정한 숫자였다.

> ⚠ 이것만으로 1번이 닫히지 않는다. 좁은 화면에서 플레이어는 여전히 단일 열의
> **맨 아래**(실측 top 1247px)에 있어 스크롤해야 보인다. 화면 밖이면 겹침이 0
> 이므로 그대로 거절된다. **§2 의 레이아웃 작업이 끝나야 1번이 닫힌다.**

### 1-b. 카세트 릴 궤도 버그 (보고 3번)

원인은 CSS 변환 합성 순서다. 개별 변환 속성(`rotate`)은 `transform` 속성보다
**나중에 합성**되므로, 한 요소가 둘을 같이 가지면 최종 행렬이
`rotate × translate` 가 되어 **translate 된 위치가 회전한다.**

| 릴     | 좌표       | 궤도 반지름 |
| ------ | ---------- | ----------- |
| 왼쪽   | (310, 327) | 450.6       |
| 오른쪽 | (589, 327) | 673.7       |

viewBox 가 `0 0 900 570` 이므로 릴이 좌상단 원점을 중심으로 큰 원을 그렸다.

**이 버그는 승인된 레퍼런스(`two-themes-v09.html` 32행)에 있다.** 포팅 실수가
아니라 레퍼런스를 충실히 재현한 결과다. 고치면 레퍼런스와 달라지므로 규칙 6 에
따라 사용자 확인을 받았다.

수정: 배치(`transform="translate(...)"`)와 회전(`rotate`)을 **다른 요소로 분리**
했다. 바깥 `<g>` 가 배치하고 안쪽 `<g class="cassette-spool">` 이 회전한다.
안쪽에는 자기 `transform` 이 없으므로 `fill-box` 의 중심이 곧 릴의 중심이다.

좌표·색·속성은 하나도 바꾸지 않았다. 레퍼런스 일치 테스트가 이를 증명한다 —
`applyIntendedChanges()` 에 이 그룹 분리만 의도된 차이로 등록했고, 그 외 모든
바이트가 여전히 일치해야 통과한다.

## 2. 1·4·5 의 공통 뿌리

### 현재 구조

`WidgetHost.vue` 의 그리드:

```
넓은 화면 (>1100px)        좁은 화면 (≤1100px)
┌──────┬────────┐          deck
│ deck │ clock  │          mascot
│ deck │ weather│          clock
│mascot│ player │          weather
└──────┴────────┘          player   ← 맨 아래
```

좁은 화면에서 **플레이어가 마지막**이다. 실측 top = 1247px — 화면 밖이다.
그래서 `reveal()`(재생 요청 시 1회 `scrollIntoView`)이 존재한다.

`DashboardShell.vue` 의 드로어:

```css
/* 넓은 화면: 340px 열을 만들어 스테이지를 좁힌다 → 보고 4번 */
.workspace.is-drawer-open {
  grid-template-columns: minmax(0, 1fr) var(--size-drawer-width);
}

/* 좁은 화면: 스테이지를 통째로 숨긴다 → 보고 5번 */
@media (max-width: 1100px) {
  .workspace.is-drawer-open > :first-child {
    display: none;
  }
}
```

**보고 5번(세로에서 재생 불가)은 버그가 아니라 설계된 동작이다.** 드로어를 열면
플레이어가 `display: none` → 0×0 → 가드가 거절한다. 그래서 드로어 안의 "목록
전체 재생" 을 눌러도 아무 일이 없고, `.play-notice` 가 "닫고 ▶ 를 눌러주세요" 를
안내한다. 사용자는 그 안내를 찾지 못했다 — **세로 화면에 재생 경로가 사실상
없다.** 데크의 ▶ 는 SVG 그림이고 동작하는 컨트롤이 아니다 (M1-6).

### 결정 (사용자 확인)

**드로어를 "플레이어를 비켜가는 오버레이" 로 바꾼다.**

```
가로 (≥1100px)                  세로 (<1100px)
┌─────────────────────────┐      ┌───────────┐
│ ┌──────┐   ╔══════════╗ │      │ ┌───────┐ │ ← 플레이어는
│ │PLAYER│   ║ LIBRARY  ║ │      │ │PLAYER │ │   항상 보임
│ └──────┘   ║(overlay) ║ │      │ └───────┘ │
│ ┌────┬────┐║          ║ │      │╔═════════╗│
│ │DECK│CLK │╚══════════╝ │      │║ LIBRARY ║│ ← 아래쪽만
│ └────┴────┘             │      │║(sheet)  ║│   오버레이
└─────────────────────────┘      │╚═════════╝│
                                 └───────────┘
```

### ⚠ 반드시 지켜야 하는 제약

`measurePlayerVisibility()` 는 **뷰포트와의 겹침만** 본다. **다른 요소가 위에
덮은 것은 감지하지 못한다.** 지금은 드로어를 형제 열로 둬서 "절대 겹치지
않는다" 를 구조로 보장하고 있다.

오버레이로 바꾸면 그 보장이 사라진다. **오버레이가 플레이어를 덮으면 소리는
나는데 영상은 안 보이는 상태**가 되고, 그것이 III.I.9 가 금지하는 바로 그
상태다. 따라서:

1. **오버레이는 플레이어 영역을 덮지 않는다.** 레이아웃으로 보장한다.
2. 그 보장을 **테스트로 고정한다.** 사각형 겹침 계산을 단위 테스트로 둔다.
3. 가리는 것이 불가피한 경우에는 기존 `playerWillHide()` 통지를 유지한다.

### 그래서 레이아웃이 선행한다 (보고 1·2번)

오버레이가 플레이어를 비켜가려면 **플레이어가 화면 안에 있어야** 한다. 사용자
제안과 같은 방향이다.

- 영상 영역을 **위로** 올린다
- 데크(LP·카세트)와 플레이어 **크기를 줄인다**
- **스크롤 없이 한 화면**에 위젯이 들어가게 한다
- 가로는 **3열**, 세로는 **2열** 배치를 검토한다 (보고 2번)

## 3. 라이브러리 재설계 (보고 6·7번)

### 현재 문제

드로어 한 열에 전부 쌓여 있다.

```
[＋ 새 목록] [＋ YouTube 링크 추가]   ← 위계가 다른 둘이 동급
플레이리스트 목록
[▶ 목록 전체 재생] [이름 수정] [삭제]  ← '이름 수정' 이 트랙 목록 바로 위
트랙 목록                              ← 그래서 트랙 이름으로 읽힌다
```

- **6a** 노래를 추가하는 버튼을 찾기 어렵다. 두 `＋` 가 나란히 있고 하나는
  플레이리스트를, 하나는 트랙을 만든다.
- **6b** `이름 수정` 은 플레이리스트 이름을 바꾸는데 트랙 목록 바로 위에 있어
  트랙 이름으로 읽힌다.
- **6c** **트랙 이름 변경 기능이 없다.** 새로 만들어야 한다.
- **7** 플레이리스트와 트랙이 같은 스크롤에 있어 둘 중 하나만 길어져도 전체가
  아래로 늘어난다.

### 결정 (사용자 구상) — 플레이리스트를 위젯으로 꺼낸다

바탕화면의 **폴더 아이콘** 메타포다.

| 표면                           | 담당                                                                   |
| ------------------------------ | ---------------------------------------------------------------------- |
| **플레이리스트 위젯**          | 플레이리스트 타일 격자. 생성·삭제. 내부 스크롤                         |
| **플레이리스트 편집 오버레이** | 한 플레이리스트의 트랙. 이름 변경, 레코드 추가·삭제·순서·**이름 변경** |

이 분리가 6·7 을 동시에 푼다.

- 6a: `＋ 새 목록` 은 플레이리스트가 사는 **위젯**으로, `＋ YouTube 링크 추가` 는
  트랙이 사는 **편집 오버레이**로 간다. 위계가 공간에 드러난다.
- 6b: `이름 수정` 은 편집 오버레이의 **머리말**로 간다. 무엇의 이름인지 자명해진다.
- 6c: 트랙 행에 이름 변경을 더한다.
- 7: 두 표면이 각자 스크롤한다. 한쪽이 길어져도 다른 쪽을 밀지 않는다.

### 상호작용

- **타일 누르기 → 그 플레이리스트 전체 재생**
- **타일 열기 → 편집 오버레이** (사용자 구상: 롱프레스 또는 다른 동작)

> `⋯`)을 두고, 롱프레스·우클릭은 그 버튼의 **추가 경로**로만 둔다.

## 5. 작업 순서 (제안)

레이아웃이 오버레이의 전제이고, 오버레이가 세로 재생의 전제다.

1. **M6-1 레이아웃** — 데크·플레이어 축소, 플레이어를 위로, 한 화면에 (1·2번)
2. **M6-2 오버레이 드로어** — 플레이어를 비켜가는 배치 + 겹침 금지 테스트 (4번)
3. **M6-3 세로 재생 경로** — 2 가 끝나면 자연히 열린다. 안내 문구 정리 (5번)
4. **M6-4 플레이리스트 위젯** — 타일 격자, 생성·삭제, 재생 (7번)
5. **M6-5 편집 오버레이** — 트랙 관리 + **트랙 이름 변경** (6번)

## 6. 아직 검증되지 않은 것

- **실제 재생(`PLAYING`) 외의 상태 전이** — `PAUSED`·`ENDED` 는 실기기에서
  확인하지 못했다. 사용자가 "유튜브 재생은 된다" 고 확인한 것이 처음이다.
- 위 1-a·1-b 수정은 **단위 테스트로만 확인했다.** 실기기 재확인이 남아 있다.
