## 0. 전제 정정 — 지금 무엇이 유실되는가

"재접속하면 플레이리스트가 날아간다"는 전제는 **사실이 아니다.** 라이브러리는
`localStorage` 에 저장되고, 새로고침 후 복원은 통합 플로우 11 번으로 검증됐다.

실제로 유실되는 경우는 다음 다섯 가지이며, 계정이 해결하는 것은 뒤쪽 세 개다.

| 상황                                             | 지금    | 계정이 해결하는가       |
| ------------------------------------------------ | ------- | ----------------------- |
| 새로고침 · 탭 닫고 다시 열기                     | 보존    | — (이미 해결)           |
| 같은 브라우저 재시작                             | 보존    | — (이미 해결)           |
| **브라우저 사이트 데이터 삭제 · 시크릿**         | 유실    | **해결**                |
| **다른 기기 · 다른 브라우저**                    | 안 보임 | **해결**                |
| **origin 변경** (`localhost:5173` ↔ 배포 도메인) | 안 보임 | **해결** (단 §3.2 선행) |

마지막 항목이 중요하다. `localStorage` 는 **origin 단위**다. 지금 개발
서버에서 만든 플레이리스트는 배포 도메인에서 보이지 않는다. 계정 없이는
**배포 주소를 한 번 정하고 바꾸지 않는 것** 외에 방법이 없다.

→ 따라서 이 기획의 목표는 "새로고침 보존"이 아니라
**기기 간 동기화 + 데이터 삭제 내구성**이다.

# A. 날씨 도시 선택

서버가 필요 없다. 트랙 B 와 **독립적으로 먼저 출하할 수 있다.**

## A.1 확인한 사실 (2026-11-04 실측)

Open-Meteo 는 **지오코딩 API 도 키 없이** 열려 있다.

```
GET https://geocoding-api.open-meteo.com/v1/search
      ?name=Seoul&count=5&language=ko&format=json
```

| 항목       | 실측 결과                                                                         |
| ---------- | --------------------------------------------------------------------------------- |
| API 키     | **불필요**                                                                        |
| CORS       | `access-control-allow-origin: *` — 브라우저에서 직접 호출 가능                    |
| 응답 필드  | `id` `name` `latitude` `longitude` `country` `admin1` **`timezone`** `population` |
| 레이트리밋 | `X-RateLimit-Limit: 600` / `Window: 60` — 분당 600 회, 요청당 비용 1.0            |
| 현지화     | `language=ko` 로 `서울특별시` · `대한민국` 반환                                   |

**`timezone` 이 응답에 있다.** 도시를 고르면 시간대를 추론 없이 알 수 있다 —
A.3 의 시계 연동이 가능해지는 근거다.

**한글 입력은 불완전하다.** 실측: `부산` 2건 · `도쿄` 1건 · **`서울` 0건**
(`Seoul` 은 정상). 색인이 로마자 표기에 더 의존한다. 설계에 반영한다 (A.6).

## A.2 [결정 필요] 컨트롤을 어디에 두는가

**승인된 디자인에 도시 선택 컨트롤이 없다** (`AGENTS.md` 규칙 6).
ADR 0013 은 "도입할 때는 컨트롤 디자인과 영속화를 함께 확정해야 한다"고
미뤄 두었다. 그 결정을 지금 해야 한다.

| 안                                            | 새 UI 면적 | 평가                                                                             |
| --------------------------------------------- | ---------- | -------------------------------------------------------------------------------- |
| **`.weather-note` 의 지명을 버튼으로** (추천) | 최소       | 이미 `WEATHER / SEOUL · OPEN-METEO` 가 있는 자리다. 새 아이콘·영역이 안 늘어난다 |
| 설정 드로어 신설                              | 큼         | 라우팅·골격이 늘어난다. 설정 항목이 1~2개뿐인데 과하다                           |
| 위젯 호버 시 기어 아이콘                      | 중간       | 터치 기기에 호버가 없다. 두 테마 모두에 아이콘 디자인이 필요하다                 |

추천안: `SEOUL` 을 버튼으로 바꾸고, 누르면 그 자리에 검색 입력이 펼쳐진다.
폼 마크업·검증·오류 표시는 **드로어의 기존 링크 추가 폼 패턴을 재사용**한다
(`RecordLibraryDrawer.vue` 의 `label`/`input`/오류 문구 구조).

> 디자인 변경이므로 **사람의 승인이 필요하다.** 승인 전에는 구현하지 않는다.

## A.3 [결정 필요] 시계도 따라가는가

시계는 지금 `Asia/Seoul` · `SEOUL, KOREA` 고정이다 (`clockFormat.ts`).

| 안                                | 결과                      | 비용                                                                    |
| --------------------------------- | ------------------------- | ----------------------------------------------------------------------- |
| **위치 하나가 둘 다 지배** (추천) | 도쿄를 고르면 시계도 도쿄 | `CLOCK_TIME_ZONE`·`CLOCK_REGION_LABEL` 이 상수→주입값. 시계 테스트 개편 |
| 날씨만 변경                       | 도쿄 날씨 + 서울 시각     | 거의 없음                                                               |

추천 근거: 두 위젯이 다른 곳을 가리키면 **버그로 보인다.** ADR 0013 도
"두 위젯이 같은 곳을 가리켜 일관된다"를 서울 고정의 근거로 삼았다. 지오코딩
응답의 `timezone` 을 그대로 쓰면 추론이 없다.

**12시간 표기는 유지한다.** 승인된 디자인의 표시 규칙이며 지역 설정이 아니다.

## A.4 영속화

새 키를 하나 추가한다. 기존 `defineStorage` 를 그대로 쓴다.

```
STORAGE_KEYS.location = '39page.location'
{ "version": 1, "data": { "name": "서울특별시", "country": "대한민국",
                          "latitude": 37.566, "longitude": 126.9784,
                          "timeZone": "Asia/Seoul" } }
```

- **키를 분리하는 이유**: 기존 규약이 용도별 분리다. 위치 변경이 테마나
  라이브러리 쓰기를 유발하지 않게 한다 (`SYSTEM_DESIGN.md` §7).
- **보호 등급은 테마와 같다.** 값이 하나고 다시 고르면 된다. ADR 0007 의
  `protected` 는 적용하지 않는다 — 그건 사용자가 축적해 복구 불가한
  데이터에만 쓴다.
- 저장값이 **없을 때만** 서울이 기본값이다. 실패했을 때 서울로 되돌리지
  않는다 (A.6).

## A.5 캐시와 요청 규율 — 빠지기 쉬운 함정

현재 `useWeather` 의 모듈 캐시는 **슬롯 하나**다 (`WEATHER_CACHE_MAX_AGE_MS`).
도시가 바뀔 수 있게 되면 이 캐시가 **이전 도시의 날씨를 새 도시의 날씨로
보여준다.** ADR 0013 §3 이 금지한 "가짜 데이터를 정상 결과처럼 보여주는 것"에
정확히 해당한다.

- 캐시 키를 `${latitude},${longitude}` 로 바꾼다. 또는 도시 변경 시 비운다.
- 지오코딩 검색: 최소 2자, 300ms 디바운스, 진행 중 요청 `abort`, `count=5`.
  폼이 열려 있을 때만 호출한다.
- 도시 변경 시 날씨 요청을 즉시 1회 보내고, 기존 15분/2분 주기를 재시작한다.

## A.6 실패 표시 — 상태가 하나 늘어난다

지오코딩이 `loading`/`ready`/`error` 에 **`no-results`** 를 추가한다.

| 상황                   | 표시                                                                       |
| ---------------------- | -------------------------------------------------------------------------- |
| 검색 결과 0건          | `찾는 도시가 없어요. 영문 표기로도 검색해 보세요.` ← 한글 색인 불완전(A.1) |
| 지오코딩 요청 실패     | `도시를 검색할 수 없어요.` — **선택을 바꾸지 않는다**                      |
| 선택 후 날씨 요청 실패 | 기존 `network`/`http`/`malformed` 경로 그대로                              |

**실패 시 서울로 조용히 되돌리지 않는다.** 사용자가 고른 곳을 유지하고
오류를 보여준다. 추측한 위치를 확정된 위치처럼 보여주지 않는다는 규칙과
같은 방향이다.

## A.7 위치 권한은 여전히 요청하지 않는다

`navigator.geolocation` 을 **쓰지 않는다.** ADR 0013 §2 와 무인 실행 지시
모두가 자동 권한 요구를 금지한다. "현재 위치" 버튼(명시적 opt-in)은 넣을 수
있지만 이번 범위에서 제외한다 — 거부 시 보여줄 것이 없고, 도시 검색으로
같은 목적을 달성한다.

## A.8 작업 분해

| 단계 | 내용                                                                | 테스트                                          |
| ---- | ------------------------------------------------------------------- | ----------------------------------------------- |
| A-1  | `geocodingApi.ts` — URL 조립, 응답 파싱·검증, 실패 분류 (순수 함수) | 단위. 불량 응답 거부, 필드 누락 거부            |

## B.1 [결정 필요] 제공자 선정 (`AGENTS.md` 규칙 8 검토)

### (a) 왜 필요한가

기기 간 동기화와 사이트 데이터 삭제 내구성. §0 의 뒤쪽 세 상황.

### (b) 직접 구현 또는 기존 의존성으로 가능한가

## B.2 [결정 필요] SDK 를 넣는가

| 안                        | 의존성 | 직접 해야 하는 일                                                   |
| ------------------------- | ------ | ------------------------------------------------------------------- |
| `@supabase/supabase-js`   | 1개    | 없음. 세션 저장·토큰 갱신·PKCE 처리를 라이브러리가 한다             |
| `fetch` 로 REST 직접 호출 | 0개    | PKCE `code_verifier` 생성·보관, 토큰 갱신 타이머, 만료 처리, 재시도 |

추천: **SDK.** 토큰 갱신과 PKCE 는 보안에 직접 닿는 영역이고, 직접 구현하면
우리가 틀렸을 때 조용히 로그아웃되거나 더 나쁜 일이 생긴다. 지금까지
의존성을 0개로 유지해 온 기조와는 어긋나므로 **ADR 에 근거를 남긴다.**

## B.3 라우터를 추가하지 않는다

OAuth 는 리다이렉트 대상이 필요하지만, **`/` 에서 처리할 수 있다.**
콜백으로 돌아온 URL 의 쿼리/해시를 읽어 세션을 세우고
`history.replaceState` 로 주소를 정리한다. Supabase 의 `detectSessionInUrl`
이 경로를 가리지 않는다.

→ `SYSTEM_DESIGN.md` §2 의 "라우터 없음"을 **유지한다.**
단 배포는 SPA 폴백이 되는 정적 호스팅이어야 한다.

## B.4 배포 origin — 도메인 확정됨 (2026-11-04)

**도메인: `39page.com`** (사용자 보유). 표준 origin 을 아래로 **하나만** 정한다.

```
https://39page.com          ← 표준(canonical). 모든 데이터가 여기 쌓인다
https://www.39page.com      → 위로 301 리다이렉트
http://  (모든 호스트)       → https 로 리다이렉트
```

**origin 을 하나로 못 박는 것이 이 결정의 전부다.** `localStorage` 는
스킴·호스트·포트를 모두 포함한 origin 단위이므로
`https://39page.com` 과 `https://www.39page.com` 은 **서로 다른 저장소**다.
둘을 다 열어두면 사용자가 들어온 주소에 따라 라이브러리가 갈린다.
`http` 와 `https` 도 다른 origin 이다.

OAuth 리다이렉트 URL 등록 목록은 **둘만** 둔다.

| 용도 | URL                     |
| ---- | ----------------------- |

## B.5 데이터 모델 — 사용자당 문서 하나

```sql
create table public.libraries (
  user_id    uuid primary key references auth.users on delete cascade,
  version    int         not null,          -- 기존 저장 봉투의 version 그대로
  data       jsonb       not null,          -- 기존 LibraryData 그대로
  revision   bigint      not null default 1,-- 단조 증가. 충돌 판정용
  device_id  text,                          -- 마지막으로 쓴 기기
  updated_at timestamptz not null default now()
);

alter table public.libraries enable row level security;

create policy "owner reads and writes own row" on public.libraries
  for all to authenticated
  using (auth.uid() = user_id) with check (auth.uid() = user_id);
```

**왜 관계형으로 쪼개지 않는가**

| 안                                     | 평가                                                                                                                        |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **사용자당 `jsonb` 문서 1행** (추천)   | 기존 `{version, data}` 봉투와 **형태가 같다.** `normalizeLibraryData` 를 **그대로 재사용**한다. store 변경 0                |
| `playlists` / `tracks` 테이블로 정규화 | `position` 관리, RLS 2개, 부분 동기화 코드가 생긴다. **공동 플레이리스트가 생길 때** 비용이 정당해진다 (현재 MVP 제외 항목) |

추천 근거가 핵심이다. 기존 저장 계층이 이미 "store 는 매체를 모른다"를
보장하므로, 원격 저장을 **같은 봉투 형태**로 두면 도메인 코드가 손대지 않는다.

## B.6 로컬 우선 — 가장 중요한 결정

| 안                                  | 결과                                                                                                 |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **로컬 우선 + 배경 동기화** (추천)  | `localStorage` 가 화면의 진실. DB 는 복제본. 오프라인 동작 유지. **계정 없이도 그대로 쓸 수 있다**   |
| 원격 우선 (부팅 시 DB 조회 후 렌더) | 오프라인에서 못 쓴다. 첫 페인트가 네트워크를 기다린다. `main.ts` 의 동기 복원(FOUC 방지)을 깨야 한다 |

추천안의 구체적 결과:

- `main.ts` 의 **마운트 전 동기 복원은 그대로 둔다.** 그다음에 비동기로
  pull → merge → push 한다.
- **`TypedStorage<T>` 를 비동기로 바꾸지 않는다.** 바꾸면 모든 store 로
  파급된다. 원격은 로컬 저장 **위에 얹는 별도 계층**이다.
- 계정은 **순수 추가 기능**이다. 로그인하지 않은 사용자의 경험은 변하지 않는다.

## B.7 충돌 — 조용히 덮어쓰지 않는다

`revision` 과 로컬의 `lastSyncedRevision` 을 비교한다.

| 상태                        | 처리                           |
| --------------------------- | ------------------------------ |
| 로컬 = 원격                 | 아무것도 안 한다               |
| 원격만 앞섰다 (로컬 무변경) | pull (fast-forward)            |
| 로컬만 앞섰다 (원격 무변경) | push (fast-forward)            |
| **둘 다 변했다**            | **`conflict` 상태로 들어간다** |

마지막 경우에 **last-write-wins 를 쓰지 않는다.** 한쪽 기기의 작업이
조용히 사라지는 것이 바로 ADR 0007 이 막으려던 종류의 사고다.

`conflict` 는 ADR 0007 의 `protected` 와 같은 모양으로 만든다 —
**자동 push 를 막고, 로컬 작업은 계속되며, 사용자가 명시적으로 고른다.**

제안하는 선택지: `이 기기 내용 유지` / `서버 내용 가져오기` /
`둘 다 보관`(기본). 마지막은 id 기준 합집합이고, 같은 id 가 다르면 둘 다 남기고
한쪽 이름에 `(이 기기)` 를 붙인다. **어느 쪽도 삭제하지 않는다.**

### 삭제 동기화에는 tombstone 이 필요하다

합집합 병합은 **삭제를 되살린다.** A 기기에서 지운 플레이리스트가 B 기기의
사본에 남아 있으면 병합 결과에 다시 나타난다.

→ 삭제 기록(`{id, deletedAt}`)을 **`39page.sync` 라는 별도 키**에 둔다.
`LibraryData` 스키마와 `normalizeLibraryData`, 그리고 그에 딸린 테스트를
**건드리지 않기 위해서다.** 동기화 메타데이터는 도메인 데이터가 아니다.

## B.8 ADR 0007 과의 상호작용 — 놓치면 사고가 난다

로컬 라이브러리 상태가 `protected` 이면 (원본을 읽지 못했거나 일부만 복구)
**절대로 push 하지 않는다.**

일부만 복구된 라이브러리를 올리면 **손실이 모든 기기로 전파된다.**
로컬 보호가 원격 전파를 막는 쪽으로 작동해야 한다.

## B.9 운영 위험 — 1주 비활성 정지

공식 가격 페이지 기준으로 무료 프로젝트는 **1주 미사용 시 정지**된다.

- 매일 쓰는 대시보드라면 접속 자체가 활성 신호라 정지되지 않는다.
- 2주 여행을 다녀오면 정지되어 있고, **수동으로 복구**해야 한다.
- 로컬 우선(B.6) 덕분에 **정지 중에도 앱은 완전히 동작한다.** 동기화만
  멈추며, 그 사실을 화면에 **명시**해야 한다 (조용히 실패 금지).
- 유료 플랜은 명시적 동의 없이 결제하지 않는다. 무료 플랜을 전제로 설계한다.

Workers Free 의 **일 10만 요청 한도는 Worker 호출(invocation) 을 세는 것**이라

## F.2 [결정 필요] 개인정보처리방침과 이용약관 — Google 이 요구한다

확인한 사실 (Google 공식 문서):

- 사용 스코프가 `openid email profile` 뿐이면 **전체 앱 검증(app verification)은
  의무가 아니다.**
- 그러나 동의 화면에 **앱 이름과 로고를 표시하려면 brand verification 을
  제출해야 한다.** Google 개발자 가이드는 "인증 전용으로 Sign in with Google
  을 쓰는 앱은 brand verification 을 제출해야 한다"고 적는다.
- **개인정보처리방침은 앱 홈페이지와 같은 도메인에 호스팅**되어야 하고,
  사용자에게 보이고, 동의 화면에 링크되어야 한다. 홈페이지도 공개 접근
  가능해야 한다. `localhost` 나 비 HTTPS 는 거부 사유다.

→ **`https://39page.com/privacy` 와 `/terms` 가 필요하다.** 라우터가 없으므로
(B.3) 정적 HTML 2장을 `public/` 에 두어 빌드 산출물에 포함시키는 방식을
추천한다. Vue 앱 안의 화면으로 만들 필요가 없다.

내용에 들어갈 것은 B.10 에 이미 정리되어 있다 — 저장하는 것(사용자 id,
이메일, 플레이리스트)과 저장하지 않는 것(재생 이력, YouTube 계정 연결,
분석). YouTube 임베드를 쓰므로 **YouTube/Google 의 쿠키가 설정된다는 점**을
적어야 한다.

## F.3 [결정 필요] Git 원격과 배포 방식

현재 **원격 저장소가 없다** (`git remote -v` 가 비어 있다). `main` 브랜치에
로컬 커밋만 있다.

| 안                              | 평가                                                                    |
| ------------------------------- | ----------------------------------------------------------------------- |
| **GitHub 원격 + Git 연동 배포** | **추천.** 푸시하면 빌드·배포된다. 백업도 된다 (지금은 이 기기에만 있다) |
| 로컬에서 `wrangler deploy` 수동 | 원격이 필요 없다. 그러나 **코드가 이 기기에만 있는 위험이 남는다**      |

저장소를 공개로 둘지 비공개로 둘지도 정해야 한다. publishable key 는 공개용
설계이므로 노출되어도 되지만, **secret/service_role key 는 저장소에 넣지
않는다** (어느 쪽이든).

> 무인 실행 지시에 따라 `git push` 는 자동으로 수행하지 않는다. 원격 추가와
> 첫 푸시는 사용자 확인 후에 한다.

## F.4 Supabase 커스텀 도메인 — 쓰지 않는다

확인한 사실: 커스텀 도메인은 **유료 플랜의 유료 애드온**이다. OAuth 동작에
**필수는 아니다** — 기본 `<ref>.supabase.co` 로 동작한다.

대가: Google 동의 화면에 `<ref>.supabase.co` 가 노출된다. 사용자에게
`39page.com` 이 아닌 낯선 주소가 보인다는 뜻이다.

→ 무료 플랜을 전제하므로 **기본 URL 을 쓴다.** 명시적 동의 없이 유료 결제를
하지 않는다. 나중에 Pro 로 올릴 이유가 생기면 재검토한다.

## F.5 [결정 필요] 스테이징 환경

`dev.39page.com` 같은 하위 도메인은 **또 다른 origin** 이다. 저장소가 분리되고
OAuth 리다이렉트 URL 을 추가 등록해야 한다.

→ **두지 않기를 추천한다.** 개발은 `http://localhost:5173` 으로 충분하고,
1인 프로젝트에 환경을 둘로 늘리면 등록·관리 비용만 는다.
