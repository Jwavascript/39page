## 1. 지금 저장되는 것 (실측, 2026-11-06)

설계의 출발점은 문서가 아니라 코드다. `localStorage` 키는 **두 개뿐**이다.

| 키               | 내부 버전 | 값                                                              | 소유                    |
| ---------------- | --------- | --------------------------------------------------------------- | ----------------------- |
| `39page.library` | 1         | `{ playlists: Playlist[], selectedPlaylistId: string \| null }` | `src/stores/library.ts` |
| `39page.theme`   | 1         | `ThemeKey` 문자열                                               | `src/stores/theme.ts`   |

둘 다 `defineStorage` 의 봉투 형태로 들어간다.

```json
{ "version": 1, "data": … }
```

`Playlist` = `{ id, name, tracks: Track[] }`,
`Track` = `{ id, source: 'youtube', videoId, title }`
(`src/shared/types/music.ts`).

**그 밖에 영속되는 것은 없다.** 레이아웃(`MVP_DASHBOARD_LAYOUT`)은 모듈 상수이고,
날씨는 캐시하지 않으며, 재생 큐·플레이어 상태·드로어 개폐·플레이리스트 선반의
접힘은 모두 메모리다. 검색으로 확인했다 — `src/` 안에서 `localStorage` 를
만지는 곳은 `src/shared/storage/defineStorage.ts` 하나다.

### 1-1. 문서와 코드의 차이 (정리)

| 문서                         | 문서가 말하던 것                | 코드 (지금)                      |
| ---------------------------- | ------------------------------- | -------------------------------- |
| `MVP_SPEC.md` §2 표          | F1–F9 전부 `미구현`             | **전부 구현 완료** (M1–M5)       |
| `MVP_SPEC.md` F9             | 프로토타입 키 이름을 인용       | 실제 키는 `39page.*` 두 개       |
| `SYSTEM_DESIGN.md` §7.1 TODO | "레이아웃·스킨 저장을 비워둘지" | 아직 저장하지 않는다 (변경 없음) |

F9 의 "현재 트랙" 은 **저장되지 않는다.** 프로토타입에는 있었지만 M2-1 에서
`LibraryData` 에 넣지 않았고, 재생 큐는 의도적으로 세션 상태다
(`SYSTEM_DESIGN.md` §6.1). 이 차이가 백업 범위를 정하는 근거가 된다.

## 2. 파일 포맷

### 2-1. 전체 구조

```json
{
  "format": "39page-backup",
  "schemaVersion": 1,
  "exportedAt": "2026-11-06T04:21:07.512Z",
  "app": { "name": "39page", "version": "0.0.0" },
  "data": {
    "library": {
      "version": 1,
      "data": {
        "playlists": [
          {
            "id": "b3f1…",
            "name": "MY RECORDS",
            "tracks": [
              { "id": "9ac2…", "source": "youtube", "videoId": "dQw4w9WgXcQ", "title": "ONE" }
            ]
          }
        ],
        "selectedPlaylistId": "b3f1…"
      }
    },
    "preferences": {
      "theme": { "version": 1, "data": "mono-vinyl" }
    }
  }
}
```

### 2-2. 필드

| 필드                     | 필수     | 형식                     | 거부 조건                              |
| ------------------------ | -------- | ------------------------ | -------------------------------------- |
| `format`                 | **필수** | `"39page-backup"` 고정   | 값이 다르면 **파일 전체 거부**         |
| `schemaVersion`          | **필수** | 정수 ≥ 1                 | 정수가 아니거나 지원 상한 초과 시 거부 |
| `exportedAt`             | **필수** | ISO 8601 UTC 문자열      | 형식 오류는 **경고만** (정보용)        |
| `app`                    | 선택     | `{ name?, version? }`    | 무시해도 가져오기에 영향 없음          |
| `data`                   | **필수** | 객체                     | 객체가 아니면 거부                     |
| `data.library`           | **필수** | `{ version, data }` 봉투 | 없거나 봉투가 아니면 거부              |
| `data.preferences`       | 선택     | 섹션별 봉투를 담은 객체  | 없으면 설정을 가져오지 않는다          |
| `data.preferences.theme` | 선택     | `{ version, data }` 봉투 | 유효하지 않으면 그 항목만 건너뛴다     |
| `integrity`              | 선택     | 섹션별 온전성 (§2-4)     | 온전하면 **넣지 않는다**               |
| `data.<알 수 없는 섹션>` | 선택     | 임의                     | **무시하고 목록에 알린다**             |

`app` 은 사람이 파일을 알아보기 위한 것이다. 가져오기 로직은 읽지 않는다 —
읽으면 앱 버전이 호환성 판단에 끼어들고, 그 판단은 `schemaVersion` 과
섹션 `version` 이 이미 하고 있다.

### 2-4. `integrity` — 온전하지 않은 스냅샷 (M8-2 에서 추가)

```json
"integrity": { "library": { "level": "recovered", "reason": "partial-recovery" } }
```

**왜 필요한가.** 저장된 원본을 온전히 읽지 못한 상태에서도 내보낼 수 있어야
한다 — 그때가 백업이 가장 필요한 순간이다. 그런데 그렇게 받은 파일을 나중에
**온전한 전체 백업으로 오인하면** 사용자가 잃은 것을 모른 채 덮어쓴다.

| `level`     | 뜻                                              |
| ----------- | ----------------------------------------------- |
| `complete`  | 온전하다. **이때는 필드 자체를 넣지 않는다**    |
| `recovered` | 복구본이다. 원본의 일부 또는 전부를 읽지 못했다 |

`reason` 은 다섯 가지다 — `partial-recovery` · `malformed` · `invalid` ·
`version-mismatch` · `unavailable`. 앞의 넷은 `LibraryProtectedReason` 과
**같은 값**이고(ADR 0007), 마지막은 저장소 자체를 쓸 수 없는 경우다.

| 라이브러리 store 상태       | 파일                             |
| --------------------------- | -------------------------------- |
| `status === 'ready'`        | `integrity` 없음                 |
| `status === 'protected'`    | `recovered` + `protectedReason`  |
| `status === 'unavailable'`  | `recovered` + `unavailable`      |
| `lastWriteFailure !== null` | **`integrity` 없음** (아래 참조) |

**쓰기 실패는 복구본이 아니다.** 그 경우 메모리는 저장소보다 **더** 온전하다 —
이번 세션의 변경이 저장되지 않았을 뿐이고 파일에는 그것까지 들어간다.
불완전한 쪽은 저장소이고 파일이 아니다. 다만 사용자에게는 알린다
(UI 가 "지금 내보내면 파일에는 포함됩니다" 라고 말한다).

#### 호환성 영향 — 없다

**선택 필드이므로 `schemaVersion` 은 1 그대로다** (§3-2 의 규칙). 모르는
리더는 무시하고 라이브러리를 정상 복원한다. 온전할 때 필드를 넣지 않으므로
평범한 백업 파일의 모양은 M8-1 문서의 예시와 **바이트 단위로 같다.**

M8-3 의 가져오기는 이 필드를 읽어 "이 파일은 복구본입니다" 를 미리보기에
띄운다. 읽지 못해도 가져오기 자체는 성립한다.

### 2-3. 왜 섹션마다 봉투를 또 두는가

파일 수준의 `schemaVersion` 과 섹션 수준의 `version` 은 **다른 것을 센다.**

| 버전                         | 무엇이 바뀌면 올리는가                              |
| ---------------------------- | --------------------------------------------------- |
| `schemaVersion` (파일)       | 파일의 **구조** — 섹션 이름, 필수 필드, 봉투 규약   |
| `data.library.version`       | `LibraryData` 의 **내용 스키마** (= 내부 저장 버전) |
| `data.preferences.*.version` | 그 설정 값의 내용 스키마                            |

이렇게 나눠 두면 두 가지가 공짜로 따라온다.

1. **기존 검증기를 그대로 쓴다.** `data.library` 는 `39page.library` 에 들어가는
   값과 **바이트 수준으로 같은 모양**이다. 가져오기는 봉투를 확인한 뒤
   `normalizeLibraryData(envelope.data)` 를 부르면 끝이다. M2 의 규칙을 복사하지
   않으므로 두 경로가 어긋날 수 없다 (`AGENTS.md` 규칙 7 과 같은 취지).
2. **내부 버전을 올려도 파일 포맷은 그대로다.** 라이브러리 스키마가 2 로
   올라가도 `schemaVersion` 은 1 이다. 반대도 성립한다.

### 2-5. 구현 (M8-2 · M8-3)

| 파일                                     | 성격      | 책임                                      |
| ---------------------------------------- | --------- | ----------------------------------------- |
| `src/features/backup/backupSchema.ts`    | 타입·상수 | 식별자, 파일 버전, 섹션 버전, 파일 타입   |
| `src/features/backup/createBackup.ts`    | **순수**  | 조립, `resolveBackupIntegrity`, 개수 세기 |
| `src/features/backup/readBackup.ts`      | **순수**  | 해석·검증, 크기 상한, 경고 수집 (M8-3)    |
| `src/features/backup/downloadBackup.ts`  | 브라우저  | 파일 이름, Blob, `<a download>`           |
| `src/features/backup/useBackupExport.ts` | 뷰 모델   | 내보내기 — store 읽기, 확인 흐름, 문구    |
| `src/features/backup/useBackupImport.ts` | 뷰 모델   | 가져오기 — 미리보기, 지문, 적용 (M8-3)    |
| `src/features/backup/BackupPanel.vue`    | 표현      | 시트 바닥의 `DATA` 패널                   |

**해석도 순수 함수다.** `readBackup(text)` 는 store 도 `localStorage` 도 DOM 도
만지지 않는다. 그래서 **미리보기 단계가 구조적으로 읽기 전용**이 된다 —
"승인 전에 쓰지 않는다" 를 규율이 아니라 구조로 보장한다.

**섹션 버전을 상수로 다시 적지 않는다.** `LIBRARY_STORAGE_VERSION` 과
`THEME_STORAGE_VERSION` 을 import 한다 — 다시 적으면 내부 스키마를 올릴 때
한쪽만 바뀌어 조용히 어긋난다.

**조립은 필드를 명시적으로 골라 담는다.** 객체를 그대로 복사하지 않는다.
그래야 `Track` 에 세션용 필드가 생겨도 파일로 새지 않고, 깊은 복사가 공짜로
따라온다. 파일 스키마가 **의도된 것**이 된다.

`exportedAt` 은 **호출부가 준다.** `createBackup` 은 시계를 읽지 않는다 —
그래야 결정적으로 테스트할 수 있다.

## 3. 버전과 호환성 정책

### 3-1. 파일 `schemaVersion`

| 읽은 값                | 처리                                                |
| ---------------------- | --------------------------------------------------- |
| `= SUPPORTED` (지금 1) | 정상 처리                                           |
| `< SUPPORTED`          | **읽는다.** 하위 호환을 유지한다 (§3-2)             |
| `> SUPPORTED`          | **거부.** 구조를 모르는 파일을 추측해서 읽지 않는다 |
| 정수가 아님            | 거부                                                |

상위 버전을 거부하는 것은 저장 계층의 정책과 같다 — 앞으로 되돌릴 수 없다
(`SYSTEM_DESIGN.md` §7.1). 거부는 "열 수 없다" 가 아니라 **"이 버전의 39page
로는 열 수 없다"** 로 안내한다. 파일은 사용자 손에 그대로 남는다.

### 3-2. 올리는 기준 — 선택 섹션 추가는 올리지 않는다

| 변경                                    | `schemaVersion` |
| --------------------------------------- | --------------- |
| **선택 섹션 추가** (예: `data.moments`) | **올리지 않음** |
| 선택 필드 추가                          | 올리지 않음     |
| 필수 필드 추가 · 이름 변경 · 타입 변경  | **올린다**      |
| 섹션 제거 · 섹션 의미 변경              | **올린다**      |

이 규칙이 Music Moments(M9)의 확장 경로다 (§6). 올리지 않으므로 **구형 앱도 그
파일을 읽을 수 있고**, 자기가 모르는 섹션은 건너뛰며 그 사실을 사용자에게
알린다. 올려 버리면 Moments 를 쓰기 시작한 순간부터 구형 앱이 라이브러리조차
복원할 수 없다.

### 3-3. 섹션 `version`

| 읽은 값            | 처리                                                              |
| ------------------ | ----------------------------------------------------------------- |
| `=` 내부 현재 버전 | 검증기에 그대로 넘긴다                                            |
| `<` 내부 현재 버전 | **마이그레이션이 있으면** 적용 후 검증. 없으면 그 섹션만 건너뛴다 |
| `>` 내부 현재 버전 | **그 섹션만 건너뛴다.** 다른 섹션은 계속 처리한다                 |

섹션 하나가 미래 버전이어도 **파일 전체를 버리지 않는다.** 라이브러리는 못
읽어도 테마는 읽을 수 있고, 그 반대도 있다. 다만 `data.library` 를 건너뛰면
가져올 것이 남지 않으므로 결과적으로 "가져올 수 있는 것이 없다" 가 된다.

> ⚠ 지금은 두 섹션 모두 마이그레이션이 **없다**(`defineStorage` 의 `migrate`
> 미제공). 내부 버전을 2 로 올리는 작업은 마이그레이션 함수를 **순수 함수로
> 따로 빼서** 저장 계층과 가져오기가 **같은 것을 쓰게** 해야 한다. 지금처럼
> `defineStorage` 옵션 안에만 두면 가져오기 경로가 그것을 호출할 수 없고,
> 규칙이 둘로 갈라진다. M8-1 의 결정 사항이다 (ADR 0018 §결정 6).

## 4. 백업 범위

### 4-1. 넣는 것

| 데이터              | 섹션                     | 근거                               |
| ------------------- | ------------------------ | ---------------------------------- |
| 플레이리스트와 트랙 | `data.library`           | 사용자가 직접 축적한 유일한 데이터 |
| 선택된 플레이리스트 | `data.library` 안        | `LibraryData` 의 일부다            |
| 현재 테마           | `data.preferences.theme` | 영속 설정이고 복원하면 편하다      |

`selectedPlaylistId` 를 뺄지 고민했지만 **넣는다.** `LibraryData` 의 일부이고,
빼면 봉투 모양이 저장 형태와 달라져 §2-3 의 이점이 사라진다. 존재하지 않는
id 를 가리키면 기존 정규화가 첫 목록으로 보정한다 (손실 없음).

### 4-2. 빼는 것

| 데이터                          | 왜                                        |
| ------------------------------- | ----------------------------------------- |
| `PlayerAdapter` 인스턴스        | 객체다. 직렬화 대상이 아니다 (ADR 0006)   |
| YouTube iframe 상태             | 외부 플레이어가 소유한다                  |
| 재생 큐·현재 트랙·재생 위치     | **세션 상태**다 (`SYSTEM_DESIGN.md` §6.1) |
| 로딩·오류·상태 메시지           | 일시적이다                                |
| 드로어 개폐, 선반 접힘, 폼 입력 | 화면 하나의 UI 상태다. 영속되지도 않는다  |
| 날씨 응답                       | 캐시하지 않는다. 복원할 것이 없다         |
| 대시보드 레이아웃               | **아직 영속되지 않는다.** 모듈 상수다     |

레이아웃은 백로그에서 사용자 편집이 열리면 영속 대상이 되고, 그때 선택 섹션
`data.layout` 으로 들어간다 (§3-2 규칙에 따라 `schemaVersion` 은 그대로).

### 4-3. 테마는 넣지만 적용은 선택이다

`POST_MVP_PLAN.md` §B.11 은 **동기화** 대상에서 테마를 뺐다 — 휴대폰과
데스크톱에서 다른 테마를 쓰는 것이 자연스럽다. 백업은 사정이 다르다. 백업은
"내 설정을 다시 세운다" 이므로 테마가 들어 있는 것이 유용하다.

그래서 **파일에는 넣고, 가져올 때 적용 여부를 사용자가 고른다.** 설정 섹션은
미리보기에서 별도 항목으로 보이고 끌 수 있다. 동기화 정책과 충돌하지 않는다.

## 5. 파일 이름과 크기

### 5-1. 이름

```
39page-backup-20261106-1321.json
```

`39page-backup-<YYYYMMDD>-<HHmm>.json`, **로컬 시각**. 콜론을 쓰지 않는다 —
Windows 파일 이름에서 금지 문자다. 초를 넣지 않는 대신 같은 분에 두 번
내보내면 브라우저가 `(1)` 을 붙인다.

### 5-2. 크기

| 한도                   | 값        | 근거                                                                                          |
| ---------------------- | --------- | --------------------------------------------------------------------------------------------- |
| 가져오기 **거부** 상한 | **8 MiB** | 읽기 전에 `File.size` 로 막는다. 트랙 하나가 JSON 약 150바이트이므로 8 MiB 는 5만 곡 이상이다 |
| 가져오기 **경고** 기준 | 4 MiB     | `localStorage` 가 origin 당 대개 5 MiB 다. 넘으면 저장이 실패할 수 있다고 미리 알린다         |
| 내보내기 상한          | 없음      | 저장된 것보다 커질 수 없다. 인위적으로 막으면 자기 데이터를 못 꺼낸다                         |

내보낼 때 **들여쓰기 두 칸으로** 직렬화한다. 파일이 20% 쯤 커지지만 사람이
열어볼 수 있어야 한다 — 평문이라는 사실을 알리는 기능이므로 열었을 때 읽히는
편이 정직하다. 실측에서 플레이리스트 2개·3곡이 **1,137 바이트**였다.

개수 상한(플레이리스트 N개, 트랙 M개)은 **두지 않는다.** 정당한 백업을 거부할
위험이 크고, 실제 한계는 바이트 수와 `localStorage` 용량이다. 용량은 쓰기
결과의 `quota-exceeded` 로 정확히 드러난다 (`defineStorage` 가 이미 구분한다).

## 6. Music Moments 확장 (M9)

### 6-1. 넣는 방법

```json
"data": {
  "library": { "version": 1, "data": {} },
  "moments": { "version": 1, "data": [] }
}
```

- **선택 섹션**이므로 `schemaVersion` 은 1 로 유지된다 (§3-2)
- 지금 버전의 앱은 이 섹션을 **무시하고 사용자에게 알린다** —
  "이 백업에는 이 버전에서 가져올 수 없는 항목(moments)이 있습니다"
- Moments 가 없는 백업을 M9 이후 앱이 읽어도 문제가 없다. 선택 섹션이므로
  없으면 가져오지 않는다

### 6-2. M9 에 넘기는 제약 (결정이 아니라 권고)

지시서가 예고한 필드는 `videoId` · 저장 시점 · 메모 · 식별자 · 생성 시각이다.
도메인 모델은 M9 에서 정한다. 다만 백업 관점에서 두 가지를 **권고**한다.

1. **Moment 는 `track.id` 가 아니라 `videoId` 를 가리켜야 한다.** `track.id` 는
   앱 내부 식별자이고 같은 영상이 여러 트랙으로 존재할 수 있다
   (`SYSTEM_DESIGN.md` §7.2). `track.id` 를 가리키면 라이브러리만 복원하거나
   Moments 만 복원했을 때 **끊어진 참조**가 생긴다.
2. **섹션 간 참조 정합성을 가져오기의 조건으로 두지 않는다.** 가리키는 영상이
   라이브러리에 없어도 Moment 자체는 유효하다. 검증을 섹션 안으로 가두면 두
   섹션의 버전을 독립적으로 올릴 수 있다.

### 6-3. M10 (Chrome 확장)과의 관계

**백업 파일을 확장과의 실시간 동기화 수단으로 쓰지 않는다.** 백업은 사용자가
명시적으로 만들고 명시적으로 가져오는 **스냅샷**이다. 확장 ↔ 웹앱 전달은
별도 설계 대상이며(`BACKLOG.md` §3), 같은 포맷을 재사용할지도 그때 정한다.

## 7. 검증 규칙 — 기존 것을 그대로 쓴다

가져오기는 **새 검증 규칙을 만들지 않는다.**

| 대상               | 재사용하는 함수                                     | 위치                             |
| ------------------ | --------------------------------------------------- | -------------------------------- |
| `LibraryData` 전체 | `normalizeLibraryData(value)`                       | `src/stores/library.ts` (export) |
| `videoId`          | `isYouTubeVideoId(value)` (위 함수가 내부에서 쓴다) | `src/shared/utils/youtube.ts`    |
| 테마 키            | `isThemeKey(value)`                                 | `src/shared/types/theme.ts`      |

`normalizeLibraryData` 는 이미 **순수 함수**이고 **무엇을 버렸는지 보고**한다.

```ts
{ data: LibraryData, report: { droppedPlaylists, droppedTracks, repairedSelection } }
```

이 `report` 가 곧 미리보기의 "가져오지 못하는 항목" 목록이다. 따로 셀 필요가
없다 — M2-1 이 이미 세고 있었다.

### 7-1. 상황별 처리

| 상황                            | 어디서 걸리는가        | 처리                                                     | 기존 데이터          |
| ------------------------------- | ---------------------- | -------------------------------------------------------- | -------------------- |
| 파일이 8 MiB 초과               | 읽기 전 `File.size`    | 거부. 파싱조차 하지 않는다                               | 영향 없음            |
| 잘못된 JSON                     | `JSON.parse`           | 거부. "JSON 파일이 아닙니다"                             | 영향 없음            |
| `format` 불일치                 | 봉투 검사              | 거부. "39page 백업 파일이 아닙니다"                      | 영향 없음            |
| `schemaVersion` 미래            | 봉투 검사              | 거부. "최신 39page 에서 가져오세요"                      | 영향 없음            |
| 필수 필드 누락                  | 봉투 검사              | 거부. 누락 필드 이름을 알린다                            | 영향 없음            |
| 중복 플레이리스트 `id`          | `normalizeLibraryData` | **처음 것만 남기고** 나머지를 버린다. 개수를 알린다      | 영향 없음 (미리보기) |
| 중복 트랙 `id`                  | `normalizeLibraryData` | 같은 플레이리스트 안에서 처음 것만 남긴다. 개수를 알린다 | 영향 없음            |
| 유효하지 않은 `videoId`         | `normalizeLibraryData` | 그 트랙만 버린다. 개수를 알린다                          | 영향 없음            |
| `selectedPlaylistId` 가 없는 id | `normalizeLibraryData` | 첫 목록으로 보정. **손실이 아니므로 경고 수준이 낮다**   | 영향 없음            |
| 섹션 `version` 미래             | 섹션 검사              | 그 섹션만 건너뛴다. 사용자에게 알린다                    | 영향 없음            |
| 알 수 없는 섹션                 | 섹션 순회              | 무시하고 이름을 알린다                                   | 영향 없음            |
| 일부만 유효                     | `normalizeLibraryData` | **명시적 동의로 부분 가져오기 허용** (§8-2)              | 동의 후에만 변경     |
| 저장 용량 초과                  | `write()` 결과         | `quota-exceeded`. 라이브러리는 **쓰이지 않았다**         | 그대로 유지          |
| 저장 중 그 밖의 오류            | `write()` 결과         | `unavailable` / `unknown`. 같은 보장                     | 그대로 유지          |

"영향 없음" 이 중요하다. **승인 전에는 `localStorage` 를 한 번도 만지지
않는다.** 모든 검사는 메모리의 값에 대해 일어난다.

## 8. 데이터 보호

### 8-1. 미리보기까지는 읽기 전용이다

```
파일 선택 → 크기 검사 → JSON.parse → 봉투 검사 → 섹션 검증 → 미리보기
                                                                  ↑
                                              여기까지 localStorage 접근 0
```

이 흐름은 저장 계층의 "읽기는 쓰지 않는다" 와 같은 성질을 가져오기에도
적용한 것이다 (`SYSTEM_DESIGN.md` §7.1).

### 8-2. 부분 가져오기 — 허용한다 (명시적 동의)

ADR 0007 은 **일부만 복구된 `localStorage` 원본**에 대해 쓰기를 **막는다**
(`partial-recovery`). 가져오기는 **반대로 허용한다.** 모순이 아니다.

| 상황                     | 원본이 어디 있나         | 부분 반영의 결과                    |
| ------------------------ | ------------------------ | ----------------------------------- |
| `localStorage` 일부 복구 | `localStorage` **자신**  | 덮어쓰면 **원본이 영구히 사라진다** |
| 백업 파일 일부 유효      | **파일** (사용자가 보관) | 파일은 그대로 남는다                |

판단 기준이 "되돌릴 수 있는가" 로 같다. 파일은 되돌릴 수 있으므로 500곡 중
1곡의 `videoId` 가 깨졌다고 전체를 못 쓰게 만들지 않는다.

조건: **버리는 항목의 개수와 종류를 미리보기에 적고**, 사용자가 그것을 본
상태에서 승인해야 한다. 조용히 버리지 않는다.

### 8-3. 보호 상태(`protected`)의 라이브러리에 가져오기

ADR 0007 은 이 상황에 **UI 가 필요하다**고 적고 범위에서 뺐다.

> "기존 데이터를 버리고 새로 시작" 같은 명시적 조작을 제공해야 한다.
> 그 확인 UI 와 강제 초기화 액션은 이번 범위에 없다.

M8 이 그 조작이다. 가져오기는 **명시적 동의를 받은 교체**이므로 `protected`
에서도 진행할 수 있어야 한다. 그렇지 않으면 "데이터가 깨졌는데 백업으로
되살릴 수 없다" 는 가장 필요한 순간에 막힌다.

- 라이브러리 store 에 **새 액션**이 필요하다 (`replaceAll`). 평범한 수정
  경로(`createPlaylist` 등)의 보호는 그대로 둔다
- 확인 문구가 **읽을 수 없는 원본을 덮어쓴다는 사실**을 말해야 한다
- 그 전에 **원본 원문 내려받기**를 제공한다. 우리가 해석할 수 없어도 사용자는
  보관할 수 있다 — `39page-raw-library-20261106-1321.txt`
- 성공하면 `status` 는 `ready` 가 된다. 사용자가 원본을 버리기로 결정한 것이다

### 8-4. 여러 키에 걸친 저장 — 원자성을 약속하지 않는다

`localStorage` 는 여러 키에 대한 트랜잭션을 제공하지 않는다. **완전한 원자성을
약속하지 않고**, 대신 순서와 복구를 정한다.

**쓰기 순서: 가치가 큰 것부터.**

```
1. 쓰기 전 현재 원문을 메모리에 보관한다 (localStorage.getItem 그대로)
2. 39page.library 를 쓴다        ← 되돌릴 수 없는 데이터
3. 39page.theme 를 쓴다          ← 최선 노력(best-effort)
```

| 결과            | 상태                                  | 사용자에게                                              |
| --------------- | ------------------------------------- | ------------------------------------------------------- |
| 2 실패          | 아무것도 바뀌지 않았다                | "가져오지 못했습니다. 기존 데이터는 그대로입니다"       |
| 2 성공 · 3 실패 | 라이브러리는 복원, 테마는 **이전 값** | "라이브러리를 복원했습니다. 테마는 적용되지 않았습니다" |
| 둘 다 성공      | 완료                                  | 복원 개수를 알린다                                      |

**핵심: 되돌릴 일이 없다.** `setItem` 은 키 하나에 대해서는 전부 쓰거나 전혀
쓰지 않는다. 뒤 단계가 실패해도 **앞 단계를 되돌릴 이유가 없다** — 테마는
다시 고르면 되는 값이고, 라이브러리를 되돌리면 사용자가 방금 승인한 복원을
우리가 취소하는 것이 된다.

그래도 되돌려야 하는 경우가 하나 있다: **쓰기 뒤 검증이 실패**하는 경우
(쓴 값을 다시 읽었는데 깨졌다). 그때는 1 에서 보관한 원문을 되돌려 쓴다.
메모리에만 두므로 **새 저장 키를 만들지 않는다** — ADR 0007 이 백업 키를
탈락시킨 이유(키 증가와 생애주기)를 되풀이하지 않는다.

**"실수로 가져왔다" 는 되돌리지 않는다.** 대신 확인 단계에서 **지금 데이터를
먼저 내보내기**를 한 번 누르면 되게 한다. 기능이 자기 자신으로 스스로를
보호하고, 새 키도 보존 기간 규칙도 필요 없다.

## 8-5. 구현 결과 (M8-3)

### 재생 큐 — 라이브러리를 교체하면 멈추고 비운다

문서에 정책이 없던 항목이라 여기서 정한다.

| 상황                | 큐                   | 왜                                                          |
| ------------------- | -------------------- | ----------------------------------------------------------- |
| 트랙 하나 삭제      | **유지** (기존 정책) | 큐는 스냅샷이다. 재생 중인 곡이 지워졌을 때만 멈춘다 (M3-5) |
| **라이브러리 교체** | **멈추고 비운다**    | 큐가 가리키는 라이브러리 자체가 사라졌다                    |
| 복원 **실패**       | **건드리지 않는다**  | 실패한 복원 때문에 재생을 멈추지 않는다                     |

스냅샷을 지키는 것이 오히려 혼란이 되는 유일한 경우다 — 계속 재생하면
사용자가 **목록에서 찾을 수 없는 곡**이 흐르고, 다음·이전은 없는 트랙 사이를
오간다.

코디네이터 계약에 `libraryReplaced()` 를 더했다. 가져오기는 **사실만** 알리고
멈출지 말지는 코디네이터가 정한다 — `trackRemoved()` 와 같은 구조다
(`AGENTS.md` 규칙 4).

### 미리보기 이후의 변경 — 낡은 승인으로 덮어쓰지 않는다

미리보기를 뜰 때 **지문**을 떠 두고 적용 직전에 다시 떠서 비교한다.

```
지문 = { store 상태, 39page.library 원문, 39page.theme 원문 }
```

저장소 **원문**까지 보는 이유: 다른 탭이 저장소를 바꾸면 이 store 는 알지
못한다 (`storage` 이벤트를 듣지 않는다). store 만 보면 놓친다.

다르면 적용하지 않고 지문을 갱신한 뒤 "다시 확인해주세요" 를 띄운다.
미리보기는 **열린 채로 남으므로** 사용자가 비교한 뒤 다시 누를 수 있다.

### 안전한 복원을 보장할 수 없으면 막는다

보호 상태인데 저장소에 접근할 수 없으면 원본을 **꺼낼 수도, 덮어쓸 수도**
없다. 그 상태로 진행하면 "복원했다" 고 말하면서 아무것도 하지 못한다.
그래서 미리보기 단계에서 막고 이유를 적는다 — 최종 버튼이 비활성이 된다.

### 저장 계층에 더한 두 가지 읽기 전용 메서드

| 메서드        | 왜                                                                     |
| ------------- | ---------------------------------------------------------------------- |
| `raw()`       | 해석하지 못한 원본을 **파일로 넘겨주기** 위해. `read()` 로는 못 꺼낸다 |
| `available()` | `raw()` 의 `null` 이 "값 없음" 과 "저장소 못 씀" 을 구분하지 못한다    |

둘 다 쓰지 않는다. 매체를 아는 쪽이 저장 계층이므로 호출부가 `localStorage`
를 직접 만지지 않아도 된다.

## 9. 전체 교체 대 병합

| 항목             | A. 전체 교체                        | B. 병합                                                       |
| ---------------- | ----------------------------------- | ------------------------------------------------------------- |
| 구현             | 검증된 `LibraryData` 를 그대로 쓴다 | id 충돌·중복 곡·이름 중복·선택 상태 **4가지 정책**이 필요하다 |
| 데이터 손실 위험 | **현재 데이터를 잃을 수 있다**      | 낮다 (기존 유지)                                              |
| 결과 예측        | 쉽다 — 파일 그대로                  | 어렵다 — 무엇이 합쳐졌는지 설명해야 한다                      |
| 되돌리기         | 내보내기 선행으로 보완              | 되돌리기가 더 어렵다 (무엇을 뺄지 모른다)                     |
| 테스트 표면      | 작다                                | 조합이 많다                                                   |

### 추천: M8 은 **전체 교체만** 지원한다

- 요청의 본질은 "데이터가 날아갈까" 에 대한 답이다. 교체만으로 **백업과 복원이
  완결된다.** 기기 이전·사이트 데이터 삭제 복구가 모두 교체로 해결된다
- 교체의 유일한 위험(현재 데이터 손실)은 **확인 단계 + 내보내기 선행**으로
  막는다. 병합의 위험(예측 불가능한 결과)은 UI 로 막기 어렵다
- 병합이 실제로 필요한 때는 **두 기기에서 각각 쌓은 목록을 합치는 것**이고,
  그것은 동기화의 문제다 (`POST_MVP_PLAN.md` §B). 백업 파일로 흉내내면
  충돌 해결 UI 를 두 번 만들게 된다

병합을 나중에 더할 때를 위해 **포맷은 바꿀 필요가 없다.** 같은 파일로 교체도
병합도 할 수 있다. 가져오기 방식은 포맷이 아니라 **적용 단계의 선택지**다.

병합을 설계할 때 정해야 할 것(지금 정하지 않는다): 같은 `id` 의 플레이리스트를
덮어쓸지 둘 다 둘지, 같은 `videoId` 를 중복으로 볼지, 같은 이름을 어떻게 구분해
보일지, 선택 상태를 누구 것으로 둘지.
